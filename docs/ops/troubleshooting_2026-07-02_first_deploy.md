# 트러블슈팅 기록 — Phase 8 최초 배포 (2026-07-02)

Phase 8(OCI 서버 배포)을 처음 실제로 진행하며 겪은 문제들을 순서대로 정리한다. 각 문제는 "가이드대로 했는데 안 됨" → "원인 확인" → "해결"의 흐름이었다. 세부 기술 로그는 [session-log/2026-07-02.md](../session-log/2026-07-02.md) 참고, 실제 적용된 최종 절차는 [guide_phase8_deploy.md](../guides/guide_phase8_deploy.md)에 반영되어 있다.

---

## 1. ARM 서버 생성이 계속 실패함 — "Out of host capacity"

**증상**: `terraform apply`를 실행하면 네트워크(VCN, 서브넷 등)는 만들어지는데, 정작 서버(VM) 생성 단계에서 "용량이 없다"는 에러로 반복 실패.

**원인**: OCI가 무료로 제공하는 ARM 서버(Always Free)는 인기가 많아서, 리전에 재고가 없으면 계속 실패한다. 특히 오사카처럼 작은 리전은 재고 자체가 적다.

**해결**: 계정을 유료 결제 티어로 전환. 이러면 무료 한도 안에서 쓰는 리소스는 여전히 과금 없이 무료지만, 서버 재고를 배정받는 우선순위가 올라간다. 전환 후 재시도해서 성공.

---

## 2. 서버는 만들어졌는데 IP 할당 충돌

**증상**: 서버 생성은 성공했지만, 그다음 "고정 IP" 만드는 단계에서 "이미 IP가 할당되어 있다"는 에러.

**원인**: 서버가 만들어질 때 임시 IP가 자동으로 하나 붙는데, 코드가 이를 모르고 별도로 고정 IP를 또 붙이려다 충돌.

**해결**: 서버 생성 시 임시 IP를 아예 받지 않도록 설정 변경, 고정 IP(`161.33.45.200`)만 쓰도록 정리.

---

## 3. 서버 초기 세팅 스크립트가 중간에 멈춤

**증상**: 서버에 필요한 프로그램(Docker, k3d 등)을 설치하는 스크립트를 돌렸는데, 절반쯤 실행하다 에러로 중단.

**원인**: Docker를 쓰려면 권한 설정이 필요한데, 이 권한은 서버에 다시 로그인해야 반영된다. 근데 스크립트는 같은 접속 세션 안에서 계속 진행하려다 권한 없음 에러로 멈췄다.

**해결**: 서버에 재접속한 뒤 스크립트를 처음부터 다시 실행.

---

## 4. 데이터베이스 초기화 설정이 실제 파일 구조와 안 맞음

**증상**: 서버에서 데이터베이스를 처음 띄울 때 필요한 초기 데이터(계정, 퀘스트 목록 등)를 넣는 설정이 실제 파일들과 안 맞았음.

**원인**: 가이드 문서를 작성할 당시엔 초기화 파일이 1개였는데, 지금은 퀘스트 세트가 늘어나면서 17개 파일로 나뉘어 있었다. 문서가 그 변화를 못 따라간 상태.

**해결**: 파일 하나가 아니라 폴더 전체를 읽도록 설정 수정.

---

## 5. 서버 실행 명령이 파일을 못 찾음

**증상**: 서버를 띄우는 명령을 실행하면 "환경설정 파일을 못 찾겠다"는 경고와 함께 제대로 안 뜸.

**원인**: 서버 실행 명령을 특정 폴더 안에서 실행했는데, 그 안에 있는 설정들이 "여기서부터 몇 칸 위 폴더에 있는 파일을 봐라"고 적혀있어서, 실행 위치에 따라 경로 해석이 어긋났다.

**해결**: 실행 명령에 "기준이 되는 폴더는 프로젝트 최상위 폴더다"라고 명시하는 옵션을 추가.

---

## 6. 백엔드 서버가 계속 재시작을 반복함 (두 단계로 발견)

**증상**: 다른 문제를 다 고쳤는데도 핵심 서버(backend)가 뜨자마자 몇 초 만에 죽고 다시 뜨기를 반복.

**원인 (1단계)**: 이번에 새로 추가한 기능(가상 실습 클러스터, vcluster)이 필요로 하는 프로그램이 서버 컨테이너 안에 설치가 안 되어 있었음. "그런 프로그램 없다"는 에러.

**해결 (1단계)**: 그 프로그램을 서버 컨테이너 만들 때 함께 설치하도록 수정.

**원인 (2단계)**: 프로그램은 설치됐는데, 이번엔 "어느 클러스터에 접속해야 하는지 설정을 못 찾겠다"는 에러. 설정 파일 자체는 있는데 그 프로그램이 표준적으로 찾는 위치가 아니었음.

**해결 (2단계)**: "이 경로를 봐라"라고 알려주는 값을 하나 추가.

---

## 7. 로그인하면 405 에러

**증상**: 웹사이트 화면 자체는 뜨는데, 로그인 버튼을 누르면 "405 Not Allowed"라는 에러가 남.

**원인**: 웹 요청을 실제 서버로 전달해주는 관문(nginx)의 설정이, 처음부터 실제 서버 주소 체계와 안 맞게 짜여 있었다. "이 특정 패턴의 주소만 서버로 보내라"는 규칙이었는데, 로그인 요청은 그 패턴에 안 걸려서 엉뚱한 곳(정적 파일 서빙)으로 가버렸다.

**해결**: 규칙을 뒤집었다 — "정적 파일(이미지, 스타일 등)이 아니면 전부 서버로 보내라"는 방식으로 재설계. 브라우저에서 로그인 성공 확인.

---

## 8. 자동 배포(CI/CD)에도 같은 문제가 숨어있었음

**증상**: GitHub에서 버튼 하나로 자동 배포하는 기능을 아직 테스트 안 한 상태였는데, 미리 점검해보니 5번(경로 문제)과 같은 실수가 자동 배포 스크립트에도 그대로 있었음.

**해결**: 실제로 자동 배포를 실행해보기 전에 미리 발견해서 같이 수정. 이후 실제 실행 테스트 성공.

---

## 결과

이 8가지를 순서대로 해결한 뒤:
- 브라우저로 서버 접속 + 로그인 성공
- GitHub Actions로 자동 배포 테스트 성공
- 로컬 DB 관리 프로그램(DBeaver)에서 서버 데이터베이스 원격 접속 성공
- 앞으로 반복될 운영 명령어들을 [guide_server_operations.md](guide_server_operations.md)로 정리

## 전체적으로 배운 것

오늘 문제들의 공통점은 대부분 **"문서/코드가 작성된 시점"과 "실제로 배포하는 시점" 사이에 프로젝트가 변해서 생긴 어긋남**이었다 (DB 파일 개수 변화, 새 기능 추가로 인한 컨테이너 요구사항 변화, API 주소 체계와 nginx 설정의 애초 불일치). 로컬 개발 환경에서는 드러나지 않다가, 실제 프로덕션처럼 여러 컨테이너가 조합되어 돌아가는 환경에서만 드러나는 문제들이 많았다 — 그래서 실제 배포 검증이 문서만으로는 대체될 수 없다는 걸 보여준 사례.
