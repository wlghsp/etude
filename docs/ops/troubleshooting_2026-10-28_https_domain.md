# 도메인 + HTTPS 적용 기록 — 서버에 무슨 일을 했나

> 2026-10-28 작성. Phase 8c([가이드](../guides/guide_phase8c_https.md) / [명세](../specs/spec_phase8c_https.md))를 실제로 진행하면서 겪은 일을, 서버 운영이 처음인 사람도 따라올 수 있게 풀어 쓴 문서다.

> 도메인·DNS·인증서가 원리상 어떻게 동작하는지는 [glossary/domain_https_how_it_works.md](../glossary/domain_https_how_it_works.md)에 따로 정리했다. 이 문서는 실제로 적용하면서 겪은 문제 기록이다.

## 한 줄 요약

`http://161.33.45.200`으로 접속하던 서비스를 **`https://etudequest.com`** 으로 옮겼다. 주소가 외우기 쉬워졌고, 로그인 비밀번호가 평문으로 오가던 문제가 사라졌다.

---

## 1. 어떤 문제가 있었나 (증상)

서버가 안 열린다고 느꼈다. 서버는 멀쩡히 켜져 있었다.

- 사용자가 주소창에 `161.33.45.200`만 치면 **브라우저가 알아서 `https://`를 붙여서** 접속을 시도한다. 요즘 브라우저는 보안을 위해 이렇게 한다.
- 그런데 서버는 **80번 문 (http)** 만 열고 있었고 **443번 문 (https)** 은 없었다. 그래서 연결이 안 됐다.
- 반대로 `http://`를 직접 써서 접속하면 열렸다. "어떤 날은 되고 어떤 날은 안 된다"처럼 보인 이유다.

더 근본적인 문제도 있었다. `http`는 **내용을 암호화하지 않는다.** 로그인할 때 이메일과 비밀번호가 인터넷을 지나는 동안 그대로 보일 수 있다.

## 2. 어떻게 풀기로 했나

"HTTPS를 쓰자"가 답이다. 그런데 HTTPS 인증서는 **숫자 주소(IP)에는 보통 발급되지 않고 도메인(이름)에 발급**된다. 그래서 도메인을 하나 샀다.

- 도메인: `etudequest.com` (회사 이름이 들어가지 않는 개인 도메인)
- 인증서: **Let's Encrypt** (무료, 대신 90일마다 갱신해야 함)

## 3. 전체 그림

```
사용자 브라우저
   │  https://etudequest.com
   ▼
[DNS] etudequest.com → 161.33.45.200      ← "이 이름은 이 주소야"라는 전화번호부
   │
   ▼
[오라클 클라우드 방화벽] 22, 80, 443번 문만 열려 있음
   │
   ▼
서버 (161.33.45.200)
   ├─ nginx 컨테이너   ← 80/443 문지기. 인증서를 들고 있고, 요청을 나눠 준다
   │     ├─ 화면 파일(frontend/dist)은 직접 내준다
   │     └─ 그 외 요청은 backend로 넘긴다
   ├─ backend 컨테이너 (Node.js)
   └─ db 컨테이너 (MariaDB)  ← 서버 안에서만 접근 가능 (외부에 안 열림)
```

## 4. 실제로 한 일 (순서대로)

| # | 한 일 | 쉬운 설명 |
|---|-------|-----------|
| 1 | 도메인 구매 | 이름을 샀다. |
| 2 | DNS에 A 레코드 등록 | "etudequest.com은 161.33.45.200이야"라고 전화번호부에 적었다. |
| 3 | 방화벽에 443번 문 열기 | Terraform 설정에 443 규칙을 추가하고 적용했다. 문이 없으면 HTTPS 요청이 들어올 수 없다. |
| 4 | 인증서 발급 | 서버에서 certbot이 "이 도메인 진짜 네 거 맞아?"를 확인받고 인증서를 받았다. |
| 5 | nginx에 HTTPS 설정 | 443번 문을 열고 인증서를 연결했다. 80번으로 오는 요청은 전부 `https://etudequest.com`으로 돌려보낸다. |
| 6 | 자동 갱신 설정 | 90일 뒤에 사람이 기억하지 않아도 갱신되도록 했다. **(검증이 아직 끝나지 않았다. 아래 7번)** |

### 4번이 어떻게 동작하나 (인증서 발급)

Let's Encrypt는 도메인 주인인지 이렇게 확인한다.

1. certbot이 "이 도메인 주소 아래 `/.well-known/acme-challenge/` 에 내가 정한 파일을 놓을게"라고 한다.
2. Let's Encrypt가 인터넷에서 `http://etudequest.com/.well-known/acme-challenge/...` 를 열어 본다.
3. 파일이 보이면 "이 서버를 가진 사람이 맞구나"라고 인증서를 내 준다.

그래서 **80번 문이 인터넷에 열려 있어야 하고**, nginx가 그 경로를 내줘야 한다. nginx 설정의 `location /.well-known/acme-challenge/` 가 그 역할이다.

## 5. 중간에 부딪힌 문제들 (증상 → 원인 → 해결)

### 5-1. 인증서 확인 요청이 404 JSON으로 돌아옴

- **증상:** 확인용 파일을 만들어 놓고 `curl`로 열어 보니 "찾을 수 없음" 같은 JSON이 나왔다.
- **원인:** nginx 설정을 고쳤다고 생각했지만 **서버에는 아직 반영되지 않은 상태**였다. 고친 파일이 커밋되지 않았거나 서버에서 `git pull`되지 않았다. nginx가 그 경로를 모르니 backend(Fastify)로 넘겼고, backend가 404 JSON을 돌려준 것이다.
- **해결:** 설정을 커밋·푸시하고 서버에서 `git pull` 후 nginx를 다시 띄웠다. 이후 `ok`가 정상 응답됐다.
- **배운 점:** 서버 설정은 "내 컴퓨터에서 고쳤다"와 "서버에 올라갔다"가 다르다. 확인하는 습관이 필요하다.

### 5-2. Terraform이 서버를 통째로 바꾸려 함 (위험했다)

- **증상:** 방화벽에 443만 추가하려고 `terraform plan`을 했는데, **서버(인스턴스)를 교체하겠다**는 계획이 같이 나왔다.
- **원인:** Terraform 설정이 "Ubuntu 22.04의 **최신** 이미지"를 자동으로 찾도록 되어 있다. 그 사이 Oracle이 새 이미지를 내놓아서 설정과 서버가 다르다고 판단했다. 그대로 적용하면 **서버의 디스크(DB 데이터 포함)가 새 이미지로 교체되어 초기화될 수 있었다.**
- **해결:**
  1. 이번에는 `-target` 옵션으로 **방화벽 규칙만** 적용했다.
  2. 근본 해결로 `infra/terraform/main.tf`의 서버 리소스에 `lifecycle { ignore_changes = [source_details[0].source_id] }` 를 넣었다. "이미지 번호가 달라져도 무시해"라는 뜻이다.
  3. 이후 `plan`에 방화벽 변경만 나오는 것을 확인했다.
- **배운 점:** `terraform plan` 결과를 읽지 않고 `apply` 하면 안 된다. `-out` 으로 plan을 저장해 두고 그 파일을 적용하면 확인한 계획 그대로 실행된다. 이 plan 파일(`*.tfplan`)에는 인프라 정보가 들어 있어서 커밋하지 않도록 `.gitignore`에 넣었다.

### 5-3. 자동 갱신이 "나중에 실패할" 뻔한 방식으로 발급됨

- **원인 후보였던 것:** certbot에는 인증 방식이 여러 가지 있다. `--standalone`은 certbot이 **임시로 80번 문을 직접 쓴다.** 그런데 80번은 nginx가 이미 쓰고 있어서, 처음 발급은 nginx를 잠깐 멈추면 되지만 **갱신은 사람 없이 자동으로 돌기 때문에 충돌**한다.
- **해결:** `--webroot` 방식을 쓴다. certbot이 `/var/www/certbot` 폴더에 확인 파일만 놓고, nginx가 그 폴더를 인터넷에 내준다. nginx를 멈출 필요가 없다. 이를 위해 nginx 컨테이너에 그 폴더를 연결(마운트)했다.

### 5-4. "방화벽(iptables)에 443을 열어야 하나?"

- **궁금증:** 서버 안의 방화벽 규칙(iptables)에는 22번만 허용하고 나머지는 거절하는 규칙이 있었다.
- **답:** Docker가 연 포트(80, 443)는 이 규칙을 **거치지 않고** 지나간다. Docker가 별도의 길(NAT)을 만들기 때문이다. 그래서 iptables에 따로 규칙을 넣을 필요가 없었다.
- **같이 알아 둘 점:** 반대로 말하면 이 규칙이 Docker 포트를 보호해 주지는 않는다. DB(3306)는 `127.0.0.1`에만 연결하도록 설정해서(`127.0.0.1:3306:3306`) 서버 밖에서는 닿지 않게 막고 있다.

### 5-5. 접속은 되는데 `/me`가 401

- **증상:** 개발자 도구에서 `GET https://etudequest.com/me 401 (Unauthorized)`가 보였다.
- **원인:** 에러가 아니다. 이 서비스의 백엔드 주소에는 `/api` 같은 앞붙이가 없고, **로그인하지 않은 상태에서 `/me`를 부르면 401이 나오는 것이 정상**이다. 화면이 "로그인되어 있나?"를 확인하려고 부른 것이다.

## 6. 인증서와 갱신, 알아 둘 것

- 인증서는 **90일**짜리다. 발급은 2026-10-28경이고 현재 만료 예정일은 **2027-01-26**이다.
- certbot은 하루 두 번 확인해서 **만료 30일 전부터** 갱신을 시도한다. 이 스케줄은 서버의 `certbot.timer`가 돌린다 (`systemctl list-timers | grep certbot` 로 확인).
- 갱신이 되어도 **nginx는 새 인증서를 자동으로 읽지 않는다.** 시작할 때 읽어서 메모리에 들고 있기 때문이다. 그래서 갱신 직후 `docker exec etude-nginx nginx -s reload` 를 실행하는 "갱신 후 훅"이 필요하다. (**아직 만들지 않았다.**)

## 7. 아직 끝나지 않은 것 (정직한 현재 상태)

`sudo certbot renew --dry-run`(실제로 갱신하지 않고 연습만 해 보는 명령)이 **실패한 상태**다.

```
authorizations for these identifiers not valid: etudequest.com
```

- 지금 바로 서비스에 영향은 없다. 인증서가 2027-01-26까지 유효하기 때문이다.
- 하지만 이걸 풀지 않으면 **약 3개월 뒤 인증서가 만료되어 사이트가 다시 막힌다.** 그 전에 반드시 해결해야 한다.
- 설정(`/etc/letsencrypt/renewal/etudequest.com.conf`)은 webroot 방식과 경로가 맞았다. 실제 실패 이유(Let's Encrypt가 확인 파일을 못 읽었는지 등)는 아직 로그에서 확인하지 못했다.
- 다음에 확인할 것: 실패한 실행의 로그 앞부분, `http://etudequest.com/.well-known/acme-challenge/<테스트파일>` 이 바깥에서 열리는지, 같은 명령을 한 번 더 실행했을 때도 실패하는지.

이 문제가 풀리면 이 문서의 7번을 "해결됨"으로 고치고, 갱신 후 훅 스크립트를 만들어 마무리한다.

## 8. 나중에 직접 확인하는 명령 모음

```bash
# 인증서 만료일 확인 (서버에서)
sudo certbot certificates

# HTTPS가 응답하는지 (내 컴퓨터에서)
curl -I https://etudequest.com

# http로 들어오면 https로 돌려보내는지
curl -I http://etudequest.com

# 자동 갱신 타이머가 살아 있는지 (서버에서)
systemctl list-timers | grep certbot

# 갱신을 연습해 보기 (서버에서, 실제 갱신은 안 함)
sudo certbot renew --dry-run
```

## 9. 서비스를 고쳐서 올리는 방법 (참고)

GitHub Actions 배포는 **수동 실행**이다. push해도 자동으로 올라가지 않는다.

```bash
gh workflow run deploy.yml
```

서버에서 `git pull`, 프론트 빌드, `docker compose up -d --build backend nginx`를 순서대로 실행한다. 브라우저에서는 강력 새로고침(Cmd+Shift+R)으로 예전 파일이 남지 않았는지 확인한다.
