# 명세 — OpenStack 분야 추가 (퀴즈 전용)

> 상태: **첫 적용 완료(로컬): 분야 화면 5곳 + 단원 1 "서비스 지도"의 세트 353·354. 단원 2 "인스턴스"(세트 355·356) 추가. 단원 3 "네트워크"(세트 357·358) 추가. 단원 4 "스토리지와 이미지"(세트 359·360) 추가. 단원 5 는 아직** (2026-11-12). 사용자 방향: "기초 위주로 진행". 근거: 사용자 제안("오픈스택 카테고리 추가할까, 실습은 없는") 후 "진행". 인프라 분야에 OSP 용어 세트(55)와 Ceph·Cinder·Neutron 구분 세트(61)가 조금 있지만, OpenStack 을 체계적으로 배우는 길은 아직 없다.

## 목표

OpenStack 을 처음 접하는 구성원이 **서비스 지도 → 인스턴스 → 네트워크 → 스토리지·이미지 → 인증·운영** 순서로 개념과 용어를 익힌다. 실습(터미널)은 없고 퀴즈(객관식·빈칸·순서)만 쓴다.

## 원칙

- **분야 이름은 `OpenStack`** (분야 문자열은 `quest_set.category`, 대소문자 그대로). 새 분야 하나이고 기존 `인프라` 분야의 세트 55·61 은 그대로 둔다. 중복 주제는 피한다 (세트 55 는 제품 이름 구분, 61 은 Ceph·Cinder·Neutron 구분).
- **검증된 사실만 담는다.** 이 PC 에 OpenStack 환경이 없어서 동작을 직접 실행해 확인할 수 없다. 그래서 공식 문서(docs.openstack.org)에서 확인되는 **개념·구조·용어·상태값·CLI 이름**만 쓰고, 버전마다 다를 수 있는 세부 동작·기본값·옵션 이름은 단정하지 않는다. 확신이 없는 문제는 넣지 않는다. 이것이 이 분야 품질의 한계다.
- 배포·제품(RHV·RHOV·OSP·OCP)이나 특정 운영 환경, IP·도메인·회사·내부 시스템 이름은 넣지 않는다. 일반화된 OpenStack 개념만 다룬다.
- 세트는 퀴즈 세트(`sandbox_type = quiz`)이고 **세트당 12~15문제**다 (큰 세트를 나눈 결정과 같은 이유: [spec_split_large_quiz_sets.md](spec_split_large_quiz_sets.md)). 한 세트에 한 주제, 한 문제에 한 개념.
- **제목과 힌트에 정답(서비스 이름 등)을 넣지 않는다.** 제목은 맡은 일을 쓴다.
- 문제 형식과 품질 규칙은 기존 퀴즈와 같다: 정답은 서버가 갖고, 보기 길이에 단서가 없게 하고, 해설이 보기와 일치하고, 빈칸 칩에 정답이 둘이 되는 값을 두지 않는다.
- 레이어는 기존 구조 그대로다. 분야는 데이터이므로 서버 코드 변경이 없다.

## 단원과 세트 계획 (초안)

학습 흐름에 맞춰 단원 5개, 세트는 아래 주제로 시작한다 (세트 수와 순서는 구현 때 조정할 수 있다).

| 단원 | 세트 주제 |
|---|---|
| 1. 서비스 지도 | OpenStack 이 하는 일, 핵심 서비스(Keystone·Nova·Neutron·Cinder·Glance·Horizon)의 역할, 서비스 사이의 호출 흐름(API·메시지·DB), 프로젝트(테넌트)와 리전 |
| 2. 인스턴스 | 인스턴스(서버) 수명주기와 상태(ACTIVE·SHUTOFF·ERROR 등), 플레이버, 이미지로 만들기, 키페어·사용자 데이터, 스케줄링 개념 |
| 3. 네트워크 | 네트워크·서브넷·포트·라우터, 보안 그룹, Floating IP, 프로바이더 네트워크와 셀프서비스 네트워크 |
| 4. 스토리지와 이미지 | Cinder 볼륨·스냅샷·백업의 차이, 볼륨 붙이기·떼기, 임시(ephemeral) 디스크와 볼륨, Glance 이미지 형식, 오브젝트 스토리지 개념 |
| 5. 인증과 운영 | Keystone 의 도메인·프로젝트·사용자·역할, 토큰, `openstack` CLI 읽기 명령 읽기(`server list`, `network list` 등), 문제가 생겼을 때 어디를 먼저 볼까 |

- 단원 안 세트 순서와 단원 순서는 `unit.display_order`, `quest_set.display_order` 로 기존 규칙대로 정한다. 분야 전체에서 `display_order` 가 겹치지 않게 한다.
- 복습 세트는 만들지 않는다 (단원 복습은 보류 중: 콘텐츠를 먼저 끝낸다).

## 화면·코드가 건드리는 곳

분야 이름이 문자열로 들어 있는 화면 파일마다 한 줄씩 더한다. 서버는 변경이 없다.

| 파일 | 추가할 것 |
|---|---|
| `frontend/src/pages/SetSelect.tsx` `CATEGORY_META` | 분야 아이콘(☁️)·색. 기존 색 토큰을 쓰고 새 색을 만들지 않는다 |
| `frontend/src/characters.ts` `GEAR` | 분야를 정복하면 붙는 장비 한 줄 |
| `frontend/src/pages/Review.tsx` `CATEGORY_ICON` | 아이콘 한 줄 |
| `frontend/src/pages/FeedTab.tsx` `CATEGORY_TEXT` | 글자 색 한 줄 |
| `frontend/src/pages/Admin.tsx` `CATEGORY_ORDER` | 분야 순서 끝에 `OpenStack` |

- 분야 순서의 기준은 홈이 분야를 나열하는 방식(세트 `display_order` 순)과 Admin 의 `CATEGORY_ORDER` 두 곳이다. 홈 쪽은 데이터(`display_order`)로 정해지므로 `OpenStack` 세트를 분야 끝(현재 최대 `display_order` 뒤)에 두면 마지막에 나온다.
- `CATEGORY_META` 가 없는 분야도 기본 색으로 나오므로 이 분야가 화면에서 깨지지는 않는다. 그래도 위 5곳은 한 번에 맞춘다 (같은 정보를 흩어 두지 않기 위해 구현 때 분야 목록이 더 있는지 다시 찾는다).

## 데이터 반영

- 새 DB: `backend/db/02_quest_set.sql` 에 세트 행, `03_quest_setN.sql` 에 문제를 추가하고, 단원은 `06_units.sql`, 아이콘은 `08_set_icons.sql`, 순서는 `11_new_set_order.sql` 에 넣는다 (기존 새 세트와 같은 방식).
- 이미 있는 DB: `backend/db/migrations/2026-11-13_` 이상 이름의 가드 있는 마이그레이션 (`NOT EXISTS`, 여러 번 실행해도 안전).
- 생성은 기존 예시 생성기(`scripts/content-gen/`)를 퀴즈용으로 쓴다. 퀴즈 세트는 터미널 검증(`verify:quests`) 대상이 아니고, 문제 내용의 사실 확인은 공식 문서 대조로 한다.
- `check-content.sh`, `check-migrations.sh` 가 통과해야 한다.

## 하지 않는 것

- 실습(터미널·샌드박스) 세트, 가상 OpenStack 환경 구축.
- 분야·세트 공개 범위 제어 ([spec_visibility_categories.md](spec_visibility_categories.md) 는 결정 대기). 처음에는 전체 공개다.
- 기존 `인프라` 분야 세트의 이동·삭제, OSP·RHV 등 제품 비교.
- 단원 복습 세트, 시험형 세트.

### 단원 4 "스토리지와 이미지" (2026-11-12)

- 단원 `스토리지와 이미지`(id 39, `unit.display_order` 113)에 세트 359(Cinder 볼륨 기초: 볼륨·스냅샷·백업·서버에 붙이기, 12문제), 360(Glance 이미지 기초: 상태·포맷·공개 범위·저장 서비스 구분, 12문제). `display_order` 707·708.
- 사실 확인: Cinder 의 볼륨 관리·볼륨 백업 문서, Glance API 문서, Nova 블록 디바이스 매핑 문서를 직접 읽어 대조했다. 문서에 없는 것(예: queued·active 외의 이미지 상태 이름, 볼륨 상태값, `private`·`community` 공개 범위)은 문제에 넣지 않았다.
- 359 3번("볼륨은 한 번에 서버 몇 대에 붙는가")은 문서의 기본 설명(한 번에 한 인스턴스)을 따랐다. 멀티어태치 같은 예외 기능은 다루지 않았다.
