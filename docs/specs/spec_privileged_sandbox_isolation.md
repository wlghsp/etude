# Privileged 샌드박스 격리 명세 — 학습자 컨테이너가 호스트 root가 되지 못하게 한다

> 상태: **초안 — 설계 결정 대기** (아래 "결정 필요"). 자원 상한(조각 R)은 이 명세와 별개로 먼저 구현했다.

## 목표

`docker`, `docker-persistent`, `linux-systemd` 샌드박스의 학습자가 컨테이너 밖(호스트, 다른 컨테이너)에 영향을 주지 못하게 한다.

## 현황 (확인한 사실)

- 세 타입의 컨테이너는 `Privileged: true`로 만든다 ([terminal.ts](../../backend/src/services/terminal.ts)의 `handleDockerTerminal`, `handleSystemdTerminal`). `linux-systemd`는 추가로 `CgroupnsMode: host`와 호스트 `/sys/fs/cgroup` 읽기-쓰기 바인드를 쓴다.
- 이 타입을 쓰는 세트는 4개, 퀘스트 **38개(전체 132개의 29%)**다: `docker` 19개(세트 5, 11), `docker-persistent` 7개(세트 8), `linux-systemd` 12개(세트 10).
- 운영 서버(확인함): aarch64 Ubuntu 22.04, 커널 6.8, cgroup v2, 4 vCPU / 23GB. Docker 29.6.1은 **rootful**이고 `userns-remap`이 없으며 런타임은 `runc` 하나뿐이다. **sysbox, gVisor, Kata는 설치돼 있지 않다.**
- 같은 호스트에서 DB(`etude-db`), backend, nginx, k3d 클러스터가 함께 돈다. backend 컨테이너는 호스트 `docker.sock`을 마운트한다.

## 위험

`Privileged` 컨테이너의 root는 사실상 **호스트의 root**다. 호스트 장치와 커널 기능에 접근할 수 있어, 알려진 방법으로 컨테이너 밖으로 나갈 수 있다. 나가면 같은 호스트의 DB 데이터, `.env.prod`(JWT 비밀값 포함), 다른 컨테이너, k3d 클러스터가 모두 노출된다. 영향 범위는 앞서 좁힌 `k8s` 관리자 권한(플랫폼 안의 세션·클러스터)보다 **훨씬 크다.**

위협 모델은 [k8s 세션 권한 명세](spec_k8s_session_permissions.md)와 같다: 사용자는 사내 구성원이고, 악의보다 **실수와 호기심**이 현실적이다. 다만 실수만으로도 서버 전체 장애로 이어질 수 있는 구성이다. 이 명세는 탈출 PoC를 실행하지 않았고, 위 위험은 특권 컨테이너에 대해 널리 알려진 성질에 기댄 것이다 (이 서버에서 직접 재현한 것이 아니다).

## 조각 R: 자원 상한 (구현 완료)

탈출과 별개로, 자원 소진은 지금 바로 막을 수 있다. `docker`·`systemd`뿐 아니라 모든 샌드박스 컨테이너에 메모리, CPU, 프로세스 수 상한을 둔다 ([sandbox-limits.ts](../../backend/src/services/sandbox-limits.ts)).

| 종류 | 메모리 | CPU | 프로세스 |
|------|--------|-----|----------|
| default (linux, linux-ssh) | 512MiB | 1 | 512 |
| k8s (k8s 학습자 컨테이너, k8s-isolated) | 1GiB | 1 | 512 |
| dind (docker, docker-persistent) | 1.5GiB | 2 | 2048 |
| systemd (linux-systemd) | 1GiB | 1 | 1024 |

스왑은 쓰지 않는다. 앱과 검증 러너가 같은 값을 쓴다.

**검증 러너가 잡은 설계 오류:** 처음에는 `k8s` 학습자 컨테이너에도 512MiB를 줬는데, 전체 러너를 돌리자 세트 14(Helm) 8개가 모두 실패했다. 원인은 `helm repo add bitnami`가 큰 차트 인덱스를 파싱하다 512MiB에서 메모리 부족으로 `Killed`되는 것이었다(1GiB에서는 성공). 그래서 `k8s`만 1GiB로 올렸다. 상한을 도입할 때 러너로 퀘스트가 여전히 풀리는지 확인하는 것이 이 때문에 필요하다. 최종 상한에서 퀘스트 132개 전부 통과를 확인했다.

**한계(중요):** 이 상한은 컨테이너 탈출을 막지 못한다. `Privileged`이고 cgroup이 쓰기 가능하면 컨테이너 안에서 자기 cgroup의 상한을 올릴 수 있을 가능성이 있다. 실수나 폭주 같은 사고를 막는 안전망이지 보안 경계가 아니다.

## 선택지

| 안 | 방식 | 장점 | 한계 / 미확인 |
|----|------|------|---------------|
| **A. Sysbox 런타임** | 호스트에 Sysbox를 설치하고 해당 컨테이너를 `--runtime=sysbox-runc`로 만든다. Sysbox는 DinD와 systemd를 `Privileged` 없이, 사용자 네임스페이스로 격리해 돌린다 | 퀘스트 38개를 거의 그대로 둘 수 있다. 근본 해결에 가장 가깝다 | **아직 확인하지 못한 것:** ARM64 지원 범위와 Ubuntu 22.04 / 커널 6.8 호환, 프로젝트의 현재 유지보수 상태. 설치는 **Docker 데몬 설정 변경과 재시작**을 요구해 DB, backend, k3d가 재시작된다(점검 시간 필요). 로컬(Colima)에서 먼저 검증해야 한다 |
| **B. 격리된 별도 호스트(VM)** | 특권이 필요한 세트만 별도 VM에서 돌린다. 뚫려도 VM 안에 머문다 | 런타임에 의존하지 않는 가장 확실한 경계 | 비용과 운영 부담. backend가 원격 Docker를 쓰도록 구조 변경(원격 소켓/SSH)이 필요하다 |
| **C. 특권 제거 시도** | `linux-systemd`는 `Privileged` 없이 cgroup v2 + 필요한 capability만으로 띄운다 | 호스트 변경 없음 | **로컬에서 시험했으나 실패했다**: 비특권(cgroupns private + tmpfs), `SYS_ADMIN` 추가, AppArmor·seccomp 완화 조합이 모두 컨테이너가 종료됐고 원인은 확정하지 못했다. 서버(cgroup 드라이버 `systemd`)에서는 다를 수 있지만 단순한 해법은 아니다. DinD는 중첩 컨테이너 때문에 특권 없이는 어렵다 |
| **D. 콘텐츠 변경** | DinD 실습을 데몬 없는 도구(예: podman/buildah, 또는 이미지 레이어/레지스트리 개념을 다른 방식으로)로 바꾼다 | 특권이 필요 없다 | 현장 실습의 핵심이 Docker라 학습 내용이 달라진다. 제품 판단 영역 |
| **E. 현상 유지 + 문서화** | 조각 R만 둔다 | 비용 없음 | 탈출 위험이 그대로 |

### 추천: A를 먼저 검증하고, 안 되면 B

A는 퀘스트를 바꾸지 않고 위험을 가장 크게 줄인다. 다만 미확인 항목이 있어서 **로컬에서 Sysbox로 세트 5, 8, 10, 11이 통과하는지(검증 러너로)** 먼저 확인한다. 서버 설치는 그 결과와 점검 시간 확보 뒤에 별도 승인으로 진행한다. 검증 러너가 이미 있어서 런타임을 바꿔도 퀘스트가 그대로 통과하는지 자동으로 확인할 수 있다.

## 결정 필요

1. 위 A~E 중 방향 (추천 A 검증 후 판단)
2. A를 택하면, 서버 점검 시간(Docker 재시작으로 서비스 일시 중단)을 언제 잡을지
3. 위협 모델상 이 위험을 얼마나 시급하게 볼지 (현재 사용자가 사내 구성원이라는 점을 반영)

## 수용 조건 (A 기준 초안)

- [ ] `docker`, `docker-persistent`, `linux-systemd` 컨테이너가 `Privileged` 없이 만들어진다
- [ ] 검증 러너로 세트 5, 8, 10, 11의 퀘스트 38개가 새 런타임에서 통과한다
- [ ] 컨테이너 안에서 호스트 장치·파일(`/dev` 블록 장치, 호스트 루트)에 접근할 수 없다 (프로브로 확인, 파괴적 동작 없이)
- [ ] 런타임 설치·롤백 절차가 `docs/ops/`에 있다

## 범위 밖

- backend가 호스트 `docker.sock`을 마운트하는 구조 (backend가 뚫리면 호스트 root. 별도 검토)
- k8s 계열 샌드박스 격리 ([k8s 세션 권한 명세](spec_k8s_session_permissions.md)에서 처리됨)
