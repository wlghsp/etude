# 명세 — k8s 통신 방법 익히기 (세트 37)

> 상태: **구현 완료(로컬), 화면 확인 대기** (2026-10-30)

## 배경과 목적

세트 25 가 Service 를 만들고 이름으로 접근하는 법을 다루지만, "**왜** Service 가 필요한가", "짧은 이름이 **왜** 되는가", "포트 세 가지는 누가 쓰는가", "외부 접속 방법을 **언제** 쓰는가" 같은 통신의 원리는 빠져 있다. 직접 확인하고 원리를 고르는 방식으로 채운다.

## 제약

- 학습자 권한은 자기 네임스페이스 `edit` 와 노드·네임스페이스 읽기뿐이라 **다른 네임스페이스에 Service 를 만들어 호출하는 실습은 불가**하다. 그래서 그 부분(이름 6번)은 `resolv.conf` 의 `search` 줄을 읽어 원리를 고르는 객관식으로 다룬다.
- 샌드박스(`etude-k8s`, busybox)의 `nslookup` 은 같은 네임스페이스의 Service 도 못 찾는다고 나온다(검색 도메인 처리 문제). **`nslookup` 은 쓰지 않고** `wget` 과 `/etc/resolv.conf` 읽기로 구성했다.
- 이미지는 노드에 캐시된 `nginx`, `busybox` 만 쓴다.

## 구성 (9문제, 실습 6 + 객관식 3)

| # | 내용 | 종류 |
|---|---|---|
| 1 | Pod IP 로 다른 Pod 에 직접 접속 (`exec` + `wget`) | 실습 |
| 2 | Pod 를 지우면 IP 가 바뀌는 것 확인 (그래서 Service 가 필요) | 실습 |
| 3 | 같은 Pod 의 두 컨테이너가 `localhost` 로 통신 (`-c`) | 실습 |
| 4 | 임시 Pod(`--rm -i --restart=Never`)로 Service 이름 통신 테스트 | 실습 |
| 5 | Pod 의 `/etc/resolv.conf` 의 `search` 읽기 | 실습 |
| 6 | 다른 네임스페이스의 Service 는 `이름.네임스페이스` 로 불러야 하는 이유 | 객관식 |
| 7 | Service 의 `port` 8080 → `targetPort` 80 으로 만들기 | 실습 |
| 8 | `port`·`targetPort`·`nodePort` 의 역할 구분 | 객관식 |
| 9 | 상황에 맞는 외부 접속 방법 (`port-forward`, NodePort, Ingress) | 객관식 |

세트 25(서비스와 네트워킹) 바로 뒤에 둔다 (`display_order` 285).

## 검증

- `검증됨`: `verify:quests --set 37` 실습 6문제 통과(정답은 통과, 무행동은 실패), `verify:quiz` 증명 통과(전체 66개; 6번은 두 네임스페이스를 만들어 `db` → `bad address`, `db.<ns>` → 응답 확인, 8번은 `port`/`targetPort` 값 확인), `check-migrations.sh` 와 새 초기화 경로 통과.
- **알려진 불안정:** `verify:quests --set 37` 을 첫 실행에서는 6문제 모두 통과했으나, 재실행에서 1문제가 실패했다(어느 문제인지 확인하지 못함, 2026-10-30에 중단). Pod 시작·IP 변화 타이밍이 의심된다. 배포 전에 다시 돌려 원인을 확인한다. 2번(IP 바뀜)은 새 Pod 가 옛 IP 를 그대로 받을 가능성도 이론상 있다.
- `미검증`: 운영(vcluster)에서의 동작과 화면. 운영 클러스터의 CNI 와 DNS 설정이 로컬 k3d 와 다를 수 있다 (특히 `search` 줄 형식과 `ndots`).
