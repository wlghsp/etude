# 명세 — 단원과 복습 세트

> 상태: **1단계(단원 구조) 구현 완료(로컬), 화면 확인 대기** (2026-10-30). 2단계: 복습 세트 내용(리눅스 1단원부터)은 아직이다.

## 배경과 목적

세트가 36개를 넘으면서 홈이 "분야 → 세트 나열"만으로는 학습 흐름이 보이지 않는다. 세트를 **단원**으로 묶고, 단원 끝에 **복습 세트**를 두어 앞에서 배운 것을 섞어서 다시 짚는다. 난이도 배지는 만들지 않고, 단원 이름과 순서가 그 역할을 한다. 진행현황 2차(분야별 막대)는 **단원별 진행**으로 대신한다.

## 구조

분야(category) → 단원(unit) → 세트(quest_set). 복습 세트는 단원 안의 마지막 세트이고 `is_review` 로 표시한다.

### 데이터

- `unit` 테이블: `id`, `category`, `title`, `display_order`. 단원 이름은 이 한 곳에만 둔다 (SSOT).
- `quest_set.unit_id`: 속한 단원 (없으면 NULL, 단원 없는 세트는 분야 맨 끝에 묶음 없이 보인다). `quest_set.is_review`: 복습 세트 여부.
- 세트의 순서는 기존 `quest_set.display_order` 를 그대로 쓴다. **한 단원의 세트는 `display_order` 가 이어져야 한다** (분야 안에서 단원이 섞이지 않게).
- 단원 번호("1단원")는 저장하지 않고 분야 안에서 `unit.display_order` 순위로 화면이 계산한다.
- 초기화는 `06_units.sql`, 이미 있는 DB 는 `migrations/2026-10-30_units.sql` (둘의 내용이 같다).

### 현재 단원

| 분야 | 단원 | 세트 id |
|---|---|---|
| 리눅스 | 1 기초 | 1, 2, 3, 34, 21 |
| 리눅스 | 2 도구 다루기 | 9, 7, 15, 30, 17, 35 |
| 리눅스 | 3 네트워크와 통신 | 4, 18, 36 |
| 리눅스 | 4 운영과 장애 대응 | 24, 10, 16, 27, 32, 28 |
| 도커 | 1 Docker 기초 | 5, 11, 8 |
| k8s | 1 기초 | 6, 20, 33, 19 |
| k8s | 2 워크로드와 설정 | 12, 22 |
| k8s | 3 스토리지와 네트워크 | 13, 25, 37, 26 |
| k8s | 4 운영과 트러블슈팅 | 14, 23, 31, 29 |

(28·29 는 각 분야의 종합 점검 퀴즈로 4단원 끝에 둔다.)

## API

- `GET /quest-sets` 의 각 세트에 `unit_id`, `unit_title`, `unit_order`, `is_review` 를 더한다.
- `GET /progress` 의 각 세트에 `unitId`, `unitTitle`, `unitOrder`, `isReview` 를 더한다.
- 둘 다 정렬은 `display_order, id` 로 그대로다.

## 화면

- 홈(2026-10-30 변경): 위아래로 쌓던 분야 아코디언 대신 **분야 카드 3개를 가로 탭**으로 둔다 (진행 링·다음 세트 포함, 카드를 누르면 그 분야의 단원만 아래에 보임, 마지막에 고른 분야를 기억하고 처음에는 이어서 학습할 분야). 분야가 늘어도 한 줄 안에서 접근할 수 있다.
- 홈: 분야 아래에 **단원 소제목**(`N단원 · 이름`, 완료 `a/b` 세트)을 보이고 그 아래에 세트 카드를 둔다. 복습 세트는 카드에 "복습" 표시를 붙인다.
- 진행현황: 분야별로 **단원별 진행 막대**(완료한 세트 수 / 단원 세트 수)를 위에 보인다. 세트 목록과 완료 기록은 그대로다.

## 복습 세트 (2단계)

- 새 개념·새 도구를 넣지 않는다. 앞 단원에서 배운 것만 쓰고 **둘 이상을 섞어서** 푼다.
- 짧은 실습과 객관식을 섞고, 틀리기 쉬운 개념을 다시 짚는다.
- 기록 단위는 기존과 같이 세트 완료다.
- 순서: 리눅스 1단원 복습부터 하나씩 만들고 효과를 확인한 뒤 나머지를 만든다.

## 시간 제한 세트 (시험형, 2026-10-30)

복습 세트 같은 시험형 세트에 **카운트다운**을 둔다. 이번 조각은 시간 제한 엔진(서버 시작 시각 + 마감 검증 + 화면 카운트다운)까지다. 복습 문제 내용·종합 능력 진단은 다음 조각이다.

### 데이터
- `quest_set.time_limit_sec` (INT NULL): 있으면 시간 제한 세트, 초 단위, 세트마다 다르다. 없으면 기존 세트와 같다.
- `set_run(user_id, quest_set_id, session_id, started_at)`: 시험을 시작한 시각을 **서버가** 기록한다 (PK = 세 값, 같은 세션의 중복 시작은 처음 시각 유지). 외래 키는 두지 않는다 (`set_completion` 과 같은 이유).
- 초기화 `00_schema.sql`, 기존 DB 는 `migrations/2026-10-30_time_limit.sql` (둘의 내용이 같다).

### API
- `POST /quest-sets/:id/start { sessionId }` → `{ limitSec: number | null, remainingSec: number | null }`. 시간 제한이 없으면 둘 다 null 이고 아무것도 기록하지 않는다. 있으면 처음 호출 때 시작 시각을 기록하고, 이후 호출은 같은 시작 시각 기준의 남은 시간을 돌려준다 (새로고침해도 시간이 되돌아가지 않는다). 남은 시간은 DB 시각(`NOW()`) 차이로 계산한다.
- `GET /quest-sets` 의 각 세트에 `time_limit_sec` 을 더한다 (홈 카드에 "⏱ N분" 표시).
- 시간 제한 세트의 `POST /quest-sets/:id/answer`, `POST /grade`, `POST /quest-sets/:id/complete` 는 **마감 뒤(여유 5초) 또는 시작 기록이 없으면 거부**한다: 403 `{ error, expired: true }`. 시간 제한이 없는 세트는 영향이 없다.
- 마감 때 **푼 만큼만 기록**한다: 이미 저장된 `quest_attempt` 는 남고, 세트 완료(`set_completion`)는 모든 문제를 통과했을 때만 생기므로 일부만 푼 시험은 완료로 기록되지 않는다.

### 화면
- 세트에 들어가면 `start` 를 호출해 남은 시간을 받고, 문제 풀이 화면 상단의 시간 칩이 **남은 시간**(`mm:ss`)을 보여 준다. 마감 시각은 서버가 알려 준 남은 시간에서 만들고, 실제 시계로 흐른다 (탭을 가려도 멈추지 않는다).
- 색: 하늘색 → 남은 시간 20% 이하 주황 → 1분 이하 빨강 깜빡임. 칩 아래에 전체 시간 막대를 가늘게 둔다.
- 시험형(시간 제한 세트)에서는 힌트·풀이 탭을 숨긴다. 문제 건너뛰기(이전/다음)는 그대로 된다. (숨김은 화면 처리이고, 서버가 힌트를 막지는 않는다.)
- 마감이 되면 화면이 "시간이 끝났어요" 안내를 띄우고 지금까지 푼 기록(결과 화면)으로 넘어간다. 서버가 거부 응답(`expired`)을 줘도 같은 흐름이다.

### 검증 기준
- 서비스: 남은 시간 계산, 마감 판정(여유 5초), 시간 제한이 없으면 항상 허용, 시작 기록이 없으면 거부.
- 라우트: `start` 응답, 마감 뒤 `answer`·`grade`·`complete` 가 403 `expired`, 시간 제한이 없는 세트는 그대로.
- 화면: 타입 검사와 빌드 (화면 동작은 사용자가 확인).

## 검증

- `검증됨`: 백엔드 단위 테스트(진행현황 응답에 단원 정보, 단원이 없으면 null) 포함 전체 196개 통과, `check-migrations.sh` 통과, 새 초기화 경로(`06_units.sql`)에서 세트 37개 모두 단원 배정·끊긴 단원 없음, 프론트 타입 검사와 빌드 통과. (프론트 린트의 `Date.now()` 오류 1개와 경고 1개는 이번 변경 이전부터 있던 것)
- 새 세트를 추가할 때는 `unit_id` 도 함께 정하고(`06_units.sql` 과 마이그레이션), 단원 안에서 `display_order` 가 이어지게 한다.
- 화면 확인은 사용자가 한다 (홈 단원 묶음, 진행현황 막대).
