# 샌드박스 이미지 pull 명세 — Docker Hub 요청 한도에 퀘스트가 막히지 않게 한다

> 상태: **보류 — 실제 운영에서 429가 발생하면 착수** (2026-10-29). 코드는 없다. 아래 분석은 그때를 위한 기록이다.
>
> 보류 이유: 429는 검증 러너를 같은 세트에 반복 실행하는 중에 재현했고, 실제 학습자 사용에서 발생한 적은 없다. 사내 소수 사용자 기준의 빈도는 측정하지 않았다. 증상: 퀘스트 setup이 종료 코드 125로 실패하고 안쪽 `dockerd` 로그에 `429 Too Many Requests`가 찍힌다.

## 목표

`docker`, `docker-persistent` 샌드박스(DinD)의 퀘스트가 Docker Hub의 익명 pull 한도(429) 때문에 실패하지 않게 한다. 학습자 수나 같은 세트의 반복 실행이 늘어도 마찬가지다.

## 현황 (확인한 사실)

- **퀘스트가 받는 외부 이미지는 5개뿐이다** (세트 5, 8, 11의 SQL에서 확인): `nginx`, `hello-world`, `ubuntu`, `alpine`, `registry:2`. 모두 `docker.io`다. 세트 8의 `localhost:5000/...`는 학습자가 안에서 띄우는 레지스트리라 해당하지 않는다.
- DinD 컨테이너는 퀘스트(세션)마다 **이미지 캐시가 없는 새 `dockerd`**를 띄운다. 그래서 퀘스트마다 같은 이미지를 Docker Hub에서 다시 받는다.
- 서버의 모든 학습자와 검증 러너가 **같은 출구 IP**를 쓰므로 익명 한도를 함께 쓴다 (실제 사용량으로 한도에 닿는지는 확인하지 못했다).
- **재현됨(로컬):** 같은 세트를 반복 실행하자 안쪽 `dockerd` 로그에 `429 Too Many Requests`가 찍히고 `setup_cmd`가 종료 코드 125로 실패했다. 한도에 걸린 요청은 이미지를 받는 `HEAD .../manifests/latest`였다. 이 명세를 쓰는 중에도 시험 pull 몇 번으로 다시 한도에 걸렸다. 정확한 한도 수치와 초기화 주기는 확인하지 않았다 (Docker 정책은 바뀐다. 확인 필요).
- 학습자에게는 "환경 오류"나 채점 불가로 보인다. 원인이 한도라는 것은 서버 로그를 봐야 안다.
- `Privileged`와 Sysbox 모두 같다 ([격리 명세](spec_privileged_sandbox_isolation.md)와 별개 문제).
- 로컬 Colima에서 기본 브리지 게이트웨이는 `172.25.0.1`이었다 (`172.17.0.1`이 아님). 호스트 주소를 하드코딩하면 안 된다. 서버 값은 모른다.

## 선택지

| 안 | 방식 | 장점 | 한계 / 미확인 |
|----|------|------|---------------|
| **A. pull-through 프록시 미러** | 호스트에 `registry:2`를 프록시 모드(`REGISTRY_PROXY_REMOTEURL=https://registry-1.docker.io`)로 띄우고, DinD의 `dockerd`에 `--registry-mirror`를 준다 | 새 이미지도 자동으로 캐시된다 (목록 관리 불필요). **클라이언트가 push할 수 없어** 학습자가 캐시를 오염시킬 수 없다. 퀘스트 SQL이 이미지를 추가해도 손댈 곳이 없다 | **미확인(핵심):** 캐시된 태그(`latest`)를 pull할 때 프록시가 Hub에 매니페스트를 다시 확인하는지, 그때 Hub가 429를 주면 캐시로 서빙하는지. 확인 못 하면 한도 문제가 남는다. 시험하려다 Hub 한도에 먼저 걸려 **검증하지 못했다** |
| **B. 미리 채운 읽기 전용 미러** | 5개 이미지를 레지스트리에 한 번 넣어 두고(시드), 서빙할 때는 push를 막는다(`storage.maintenance.readonly`). DinD는 같은 `--registry-mirror`를 쓴다 | **검증됨(로컬):** Hub를 막은 DinD가 호스트의 미러만으로 `alpine`, `hello-world`를 받았다. Hub 한도와 무관하다. 목록에 없는 이미지는 Hub로 되돌아가므로 지금보다 나빠지지 않는다 | 이미지 목록과 시드 절차를 따로 관리해야 한다 (퀘스트가 새 이미지를 쓰면 시드에 추가). 쓰기 가능한 상태로 두면 학습자가 이미지를 덮어쓸 수 있어 **읽기 전용 서빙이 필수**다. 이미지가 낡는다 (갱신 절차 필요) |
| **C. 이미지 사전 탑재** | 커스텀 DinD 이미지에 5개 이미지를 tar로 넣고 시작할 때 `docker load` | 네트워크 의존이 없다 | 세션마다 수백 MB를 읽고 적재한다 (시작 지연, 메모리·디스크). 이미지 크기와 CPU 아키텍처 관리. B와 같은 목록 관리 문제 |
| **D. Docker Hub 로그인** | 유료/무료 계정으로 인증 pull | 한도가 늘어난다 | 한도 자체는 남고 서버 전체가 한 계정을 공유한다. 비밀값 관리가 늘고, DinD마다 로그인해야 한다 (학습자가 그 자격증명을 볼 수 있다) |
| **E. 현상 유지** | — | 비용 없음 | 사용자가 늘면 퀘스트가 간헐적으로 실패한다 |

### 추천: A를 먼저 검증하고, 안 되면 B

- A는 관리 부담이 가장 작고 캐시 오염도 구조적으로 막는다. 단 핵심 가정(한도에 걸려도 캐시로 서빙)을 **먼저 시험**한다. Hub 한도가 풀린 뒤, 캐시를 채우고 프록시에서 Hub를 막아 보는 방식으로 확인한다.
- A가 안 되면 B. B는 이미 검증한 동작이다. 단 읽기 전용 서빙과 시드 절차를 갖춘다.
- C, D는 추천하지 않는다 (C는 세션마다 비용, D는 비밀값을 학습자 가까이 둔다).

## 설계 (A, B 공통)

- **켜고 끄는 설정:** `SANDBOX_REGISTRY_MIRROR`(예: `http://etude-registry-mirror:5000`). 값이 없으면 지금처럼 Docker Hub에 직접 간다. [`SANDBOX_RUNTIME`](spec_privileged_sandbox_isolation.md)과 같은 방식이라, 서버에 미러가 없어도 배포는 안전하다.
- **적용 위치:** DinD 컨테이너 생성 시 `dockerd`에 `--registry-mirror`를 인자로 넘긴다 (`docker:dind`의 entrypoint가 인자를 `dockerd`로 전달한다. 로컬에서 확인). 앱의 [terminal.ts](../../backend/src/services/terminal.ts)와 검증 러너가 같은 값을 써야 하므로 [sandbox-runtime.ts](../../backend/src/services/sandbox-runtime.ts)처럼 한 헬퍼에 둔다 (단일 진실 공급원).
- **미러까지의 경로 (결정 필요, 아래):** 호스트 `127.0.0.1`에만 열면 컨테이너에서 닿지 않는다. 호스트 주소를 하드코딩하지 않는다.
- **미러를 학습자가 건드리지 못하게:** A는 프록시라 push가 거부된다. B는 읽기 전용으로 서빙한다. 미러 포트는 학습자 컨테이너에서만 닿고 바깥에는 열지 않는다.
- **로컬 시험에서 확인한 동작:** `--registry-mirror=http://<호스트>:5001`만으로 충분했고 `--insecure-registry`는 필요하지 않았다 (Docker 29, HTTP 미러, 같은 호스트).

## 수용 조건

- [ ] `SANDBOX_REGISTRY_MIRROR`가 없으면 컨테이너 생성 옵션이 지금과 같다 (단위 테스트)
- [ ] 값이 있으면 DinD 컨테이너가 `--registry-mirror`를 받고, 호스트에 닿는 경로가 설정된다 (단위 테스트)
- [ ] 캐시를 채운 뒤 **Hub를 막은 상태에서** 퀘스트가 쓰는 5개 이미지를 DinD가 pull한다 (실행 확인)
- [ ] 학습자 컨테이너에서 미러로 push하면 거부된다
- [ ] 세트 5, 8, 11의 퀘스트가 미러를 켠 상태에서 통과한다 (검증 러너)
- [ ] 같은 세트를 여러 번 연속 실행해도 `429`로 실패하지 않는다 (미러를 켠 상태)
- [ ] 미러 구성·시드/갱신·롤백이 `docs/ops/`에 있다
- [ ] 미러가 죽어도 DinD가 Hub로 되돌아가 동작한다 (지금보다 나빠지지 않는다)

## 범위 밖

- `apt`, `pip` 등 패키지 미러 (세트 11의 `RUN apt-get`은 Hub가 아니라 배포판 미러를 쓴다)
- `k8s` 계열 샌드박스의 이미지 pull (클러스터 노드가 받는다. 별도 검토)
- 퀘스트가 쓰는 이미지를 줄이거나 바꾸는 콘텐츠 변경

## 결정 필요

1. **A를 먼저 시험해도 되는지** (Hub 한도가 풀릴 때까지 기다린 뒤 시험한다. 이 사이에는 코드를 쓰지 않는다)
2. **미러까지의 경로:** (가) 사용자 정의 Docker 네트워크에 미러와 DinD를 붙이고 이름으로 접근, 호스트 포트를 열지 않는다 / (나) 호스트 `host-gateway`로 접근하고 미러 포트를 브리지 게이트웨이에만 바인딩한다. 추천은 (가)지만, DinD를 별도 네트워크에 두는 영향(샌드박스끼리의 통신 범위, 기존 기본 브리지와의 차이)을 구현 전에 확인한다.
3. 서버 출구 IP가 다른 서비스와 한도를 공유하는지 (공유한다면 미러 도입이 더 급하다)
