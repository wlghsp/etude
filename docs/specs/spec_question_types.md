# 명세 — 가벼운 문제 형식 (순서 맞추기, 빈칸 채우기)

> 상태: **구현 완료(로컬), 화면 확인 대기** (2026-10-30). 첫 콘텐츠: 도커 세트 38·39 (아래). 계기: 컨테이너가 필요한 실습은 인프라 한계(vcluster 풀, 격리 권한, 기동 시간)에 묶인다. 컨테이너 없이 서버가 정답을 판정하는 **가벼운 형식**을 늘려 콘텐츠를 충실하게 채우고, 문제 형식을 다양하게 해서 지루하지 않게 한다.

## 목적과 원칙

- 컨테이너를 만들지 않는다. 퀴즈 세트(`sandbox_type = 'quiz'`)에도, 터미널 세트 중간에도 쓸 수 있다.
- **정답은 서버만 안다.** 기존 객관식과 같이 문제 조회(`GET /quest-sets/:id/quests`)에 정답을 내보내지 않는다.
- 사용자가 직접 입력한 글자는 채점하지 않는다 (자유 서술은 보류). 모든 답은 **정해진 보기에서 고른 번호의 나열**이다.
- 접근성: 마우스 끌기 없이 **누르기만으로** 풀 수 있고 키보드로도 된다. 틀렸을 때 어느 자리가 맞았는지 알려 주어 배우게 한다.

## 형식

| `kind` | 화면 | 학습자가 하는 일 | 정답 |
|---|---|---|---|
| `choice` | 보기 중 하나 선택 | 번호 하나 고르기 | `answer_index` (기존) |
| `order` | 카드 여러 장 | 카드를 눌러 **올바른 순서**로 놓기 | `answer_spec`: 카드 번호를 올바른 순서로 나열한 배열 |
| `fill` | 명령 줄의 빈칸 + 보기 칩 | 칩을 눌러 **빈칸을 채우기** | `answer_spec`: 빈칸마다 맞는 칩 번호 |

향후 후보(이번 범위 아님): `match`(짝 맞추기), `spot`(오류 찾기), 출력 예측(객관식 변형).

## 데이터 (`quest` 테이블)

- `kind`: `'terminal' | 'choice' | 'order' | 'fill'`.
- `choices` (공개 JSON 배열): `choice` 는 보기 글, `order` 는 **섞인 순서로 저장한 카드 글**, `fill` 은 **칩 목록**(정답 칩과 헷갈리게 하는 칩을 함께 둔다).
- `template` (공개 TEXT, `fill` 전용): 명령 줄 틀. 빈칸은 `{0}`, `{1}` … 로 쓴다. 예: `kubectl {0} deployment web {1}=3`.
- `answer_spec` (**서버 전용** JSON): `order` 는 카드 번호의 올바른 순서 `[2,0,3,1]`, `fill` 은 빈칸 번호 순서의 칩 번호 `[4,1]`.
- `explanation`: 정답을 맞힌 뒤에만 보여 주는 해설 (기존과 같다). 힌트(`hint`)는 선택이다.
- 초기화 `00_schema.sql`, 기존 DB 는 `migrations/2026-10-30_00_question_types.sql` (내용 같음).
- 문제 조회는 `answer_spec` 을 읽지도 내보내지도 않는다.

## 답 제출 API

`POST /quest-sets/:id/answer` (기존 경로):

- 본문: `choice` 는 `choiceIndex`, `order`·`fill` 은 `answer`(번호 배열). `questId`, `sessionId`, `elapsedSec`, `hintUsed` 는 같다.
- 판정(`judgeAnswer`):
  - `order`: 배열 길이가 정답과 같고, 모든 값이 카드 번호 범위 안의 정수이며 **중복이 없어야** 한다. 자리마다 정답과 같은지 비교한다.
  - `fill`: 길이가 빈칸 수와 같고, 모든 값이 칩 번호 범위 안의 정수여야 한다 (같은 칩을 여러 빈칸에 쓸 수 있다). 자리마다 비교한다.
  - 형식이 틀리면 400.
- 응답: `{ passed, results?, explanation? }`. `order`·`fill` 은 `results`(자리마다 맞았는지 boolean 배열)를 오답에서도 돌려준다 (어디가 틀렸는지 알려 주기 위해). 해설은 **정답일 때만**.
- 채점 기록(`quest_attempt`)과 세트 완료 기록은 객관식과 같다. 시간 제한 세트의 마감 검사도 같이 적용된다.

## 화면 (`QuestPanel`)

- `order`: 위에 **놓는 자리**(1번, 2번 …), 아래에 **카드 묶음**. 카드를 누르면 다음 빈 자리에 들어간다. **놓은 카드끼리는 자리를 쉽게 바꾼다**: 카드의 ▲▼ 버튼(모바일·키보드용)이나 끌어서 놓기(마우스)로 위치를 옮기고, ✕ 로 묶음에 되돌린다. 모든 자리가 차면 "정답 확인"이 켜진다. 오답이면 맞은 자리는 초록, 틀린 자리는 빨강으로 보이고 틀린 카드는 묶음으로 돌아온다.
- `fill`: 명령 줄이 코드 모양으로 보이고 빈칸은 점선 칸이다. 칩을 누르면 다음 빈 칸에 들어가고, 채운 칸을 누르면 비워진다. 오답이면 맞은 칸은 초록, 틀린 칸은 빨강.
- 객관식과 같은 정답 연출(색종이, 효과음, 해설)과 "다음 퀘스트" 이동을 쓴다. 풀이(`solution`) 탭은 없다 (객관식과 같다).

## 콘텐츠 작성 기준

- 문구 기준은 `spec_quest_writing_guide.md` 를 따른다 (이름·값은 `백틱`, 왜 필요한지 → 할 일 → 완료 조건).
- `order`: 카드는 3~6장. 순서에 의미가 있는 것(절차, 파이프 조립, 장애 대응 순서)만. 카드는 **저장 순서가 정답이 아니게** 섞어 둔다.
- `fill`: 빈칸은 1~3개, 칩은 정답보다 2~3개 많게 (비슷한 명령·옵션을 함께).
- 해설은 "왜 이 순서/명령인가"를 한두 문장으로.

## 검증

- 서비스 테스트: `judgeAnswer`(순서·빈칸 정답/오답/형식 오류/중복), 조회 시 `answer_spec` 비노출·`template` 노출, 라우트(정답·오답·400·404·해설은 정답일 때만).
- 콘텐츠: 새 세트의 `answer_spec` 이 카드·칩 범위와 맞는지 검사하는 테스트(SQL 원본 대신 응답 형태로 확인).
- 화면은 타입 검사와 빌드, 실제 조작은 사용자가 확인한다.
