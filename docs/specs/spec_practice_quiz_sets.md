# 명세 — 실습 연계 객관식 세트

> 상태: **명세 승인, 세트 30 작성 완료(로컬), 화면 확인 대기** (2026-10-29). 시범: 세트 30 (리눅스) 8문제, 세트 31 (k8s) 8문제.

## 배경과 목적

개념 퀴즈(세트 28·29, [spec_quiz_sets.md](spec_quiz_sets.md))는 터미널 없이 푼다. 하지만 이 시스템의 핵심은 실습이라서, **터미널에서 직접 명령을 쳐 값을 확인하고 그 값으로 답을 고르는 문제**가 필요하다. "실습과 객관식이 공존"하는 형태다. 개념 퀴즈에 빈 터미널을 붙이는 방식은 쓰지 않는다 (터미널로 확인할 게 없는 문제에서는 혼란만 준다).

## 원칙

- **실습 연계 세트를 따로 둔다.** 세트의 `sandbox_type` 은 `linux`(이후 `k8s`)로 두어 기존 레이아웃(왼쪽 문제, 오른쪽 터미널)을 그대로 쓴다. 개념 퀴즈 세트(`quiz`)는 그대로 둔다.
- 모든 문제는 **터미널에서 확인해야만 답이 나오는 시나리오**여야 한다. 시나리오는 `setup_cmd` 가 만들고, 값은 **항상 같게 고정**한다 (정답은 서버에 고정된 `answer_index` 이므로, 실행할 때마다 값이 바뀌는 문제는 쓰지 않는다. 시간·PID·무작위·실시간 메모리 값 금지).
- 정답과 해설은 서버만 안다. 판정·기록·세트 완료는 객관식 구조(`quest.kind='choice'`, `/quest-sets/:id/answer`)를 그대로 쓴다. 새 API와 스키마 변경은 없다.
- 선택지는 **"틀리기 쉬운 값"** 으로 만든다 (옵션을 빼먹었을 때 나오는 값, 비슷한 줄 등). 해설은 정답뿐 아니라 오답이 왜 틀렸는지 쓰고, 어떤 명령으로 확인하는지 알려 준다. 문구 기준은 [spec_quest_writing_guide.md](spec_quest_writing_guide.md).
- 설명에는 **시나리오가 어디에 있는지**(파일 경로, 디렉터리)를 반드시 쓴다. 학습자가 무엇을 열어 봐야 하는지 알 수 있어야 한다.

## 시범 세트 30 (리눅스, 8문제) 문제 구상

| # | 시나리오 (setup 이 만드는 것) | 학습자가 하는 일 | 선택지 예 |
|---|------|------|------|
| 1 | `/var/log/app/app.log` (ERROR·WARN·INFO 줄 고정 개수) | `grep -c` 로 ERROR 줄 수 세기 | 12 / 7 / 19 (대소문자·WARN 포함 값) |
| 2 | `/var/log/app/access.log` (IP별 요청 수 고정) | `awk`·`sort`·`uniq -c` 로 가장 많이 요청한 IP | IP 4개 |
| 3 | `/data/` 아래 크기가 다른 하위 디렉터리 3개 | `du -sh /data/*` 로 가장 큰 디렉터리 | 디렉터리 이름 |
| 4 | `/srv/report.csv` (소유자·권한 고정) | `ls -l` 로 권한을 읽고 숫자 권한 고르기 | 640 / 604 / 460 / 064 |
| 5 | `/etc/app.conf` (설정 항목 여러 개) | `grep` 으로 `port` 값 찾기 (주석 줄 함정) | 포트 번호 4개 |
| 6 | `/tmp/words.txt` (고정 단어) | `grep -q` 후 `echo $?` 의 종료 코드 읽기 | 0 / 1 / 2 / 127 |
| 7 | `/tmp/dup.txt` (중복 줄 고정) | `sort | uniq -d` 로 중복된 줄 | 단어 4개 |
| 8 | `/opt/releases/` 아래 수정 시각이 다른 파일 (`touch -d` 로 고정) | `ls -lt` 로 가장 최근 파일 | 파일 이름 |

(주제는 초안이다. 실제 문제는 문구 기준에 맞춰 작성하고 `setup_cmd` 로 만든 값과 정답을 컨테이너에서 대조한다.)

## 세트 31 (k8s, 8문제)

세트 `sandbox_type='k8s'`. `setup_cmd` 가 `$NS` 에 고정된 상태를 만들고 학습자는 `kubectl` 로 확인한다. 이미지 태그 오타(Events 의 `not found`), `Pending`(requests 500Gi → `Insufficient memory`), 리비전 번호(이미지 2번 변경 → 3), Service selector 불일치(Endpoints 비어 있음), ConfigMap 값, Secret(base64 해독), 라벨로 Pod 개수, `exec` 로 환경변수 확인.

- 검증됨: 로컬 k3d 에서 문제마다 임시 네임스페이스에 setup 을 만들고 증명 명령을 실행해 정답 값 확인 (`npm run verify:quiz`, 증명 39개 통과). 저장된 `setup_cmd` JSON 을 임시 DB 에서 다시 읽어 구조 확인, `check-migrations.sh` 통과.
- `미검증`: 운영 서버(vcluster)에서 같은 결과가 나오는지. 특히 `Pending` 이유(노드 크기), 이벤트 문구, 이미지 pull 시간. `kubectl describe` 의 `Endpoints:` 는 이 클러스터 버전에서 `<none>` 이 아니라 빈 값으로 나온다 (해설은 "비어 있다"로 썼다).

## 세트 33 (k8s 쉬운 장애 고치기, 직접 채점형 8문제)

객관식이 아니라 기존 k8s 세트와 같은 **직접 고치고 채점하는 실습형**이다. 이미지 태그·주소 오류 고치기, ConfigMap 변경 후 `rollout restart`, `replicas` 늘리기, 없는 StorageClass 를 지정한 PVC 를 기본값으로 고치기, `rollout undo`, 컨테이너 2개짜리 Pod, `kubectl --sort-by` 로 정렬해 저장하기.

- 참고 자료: 받은 CKA 기출 형태 PDF(5문제 샘플)는 **문제를 옮기지 않고 주제만** 참고했다. 로그 필터링·DaemonSet·initContainer 는 세트 6/15/22 에 이미 있어 넣지 않았고, 없던 멀티 컨테이너 Pod(7번)와 `--sort-by`(8번)를 새 시나리오로 만들었다.
- 제외: PV 를 직접 만들어 PVC 와 연결하기(정적 프로비저닝)는 인프라 의존이 커서 뺐다. 학습자 권한이 네임스페이스 `edit` + 노드·네임스페이스 읽기뿐이라 **StorageClass 목록은 읽지 못한다** (`kubectl get storageclass` 금지). 그래서 PVC 문제는 "이름 없이 기본값 쓰기"로 설계했다. 운영에도 기본 StorageClass 가 있어야 한다 (세트 13 과 같은 전제).
- 검증됨: `npm run verify:quests -- --set 33` 8문제 모두 통과 (정답은 통과, setup 만으로는 통과하지 않음). 처음 설계(StorageClass 를 조회해 고르는 방식)는 이 권한 때문에 정답이 거부되어 바꿨다.
- `미검증`: 운영(vcluster)에서의 동작, 화면.

## 확인이 필요한 것 (구현 첫 단계)

- `미검증` 객관식 문제(`kind='choice'`)가 `linux` 세트에서 **터미널이 뜨고 `setup_cmd` 가 실행되는지**. `services/terminal.ts` 는 `kind` 와 무관하게 퀘스트 ID로 `setup_cmd` 를 조회해 실행하므로(`getSetupCmd`) 될 것으로 보이지만(`코드상 확인됨`, 실행은 아직), 객관식에 `grade_cmd` 가 `[]` 인 점과 세트별 컨테이너 수명주기(문제마다 새 컨테이너인지, 세트 지속인지)를 실제로 확인한다. 안 되면 최소 수정으로 맞춘다.
- 문제를 넘길 때 컨테이너가 새로 만들어지는 경우, 학습자가 만든 변경(예: 파일 삭제)이 다음 문제로 이어지지 않는지.

## 검증

- 서버: 기존 객관식 단위 테스트가 그대로 통과 (로직 변경이 없으면 추가 불필요). 로직을 바꾸면 해당 부분 테스트를 먼저 쓴다.
- 문제 내용: 모든 문제를 `backend/verify/` 방식으로 **실제 컨테이너에서 setup 을 돌린 뒤 증명 명령을 실행해, 나온 값이 `answer_index` 의 선택지와 같은지** 확인한다 (`npm run verify:quiz` 확장 또는 새 스크립트).
- 세트 30의 화면(터미널 + 객관식 동시 표시, 정답·오답, 완료 기록)은 사용자가 브라우저에서 확인한다.
