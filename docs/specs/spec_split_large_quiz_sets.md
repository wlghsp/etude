# 명세 — 큰 퀴즈 세트 나누기

> 상태: **도커(배포 완료)·리눅스(로컬 검증 완료) 적용, k8s·Git·데이터베이스 대기** (2026-11-12). 열린 결정은 기본안으로 확정(사용자 위임). 근거: 배포 서버 피드백 #13("문제 31개는 너무 많다, 단계별로 나눠 머리 안 아픈 구조로")과 사용자 확인("한번에 31문제 나오면 부담스럽다"). 지난번 [spec_docker_unit_split.md](spec_docker_unit_split.md) 의 "10문제씩 단계 표시"는 진행 막대만 나눌 뿐이라 부담을 줄이지 못했다. 이번에는 세트를 실제로 나눈다.

## 현황 (로컬 DB 기준)

- 문제가 26개 이상인 세트 **97개**, 모두 퀴즈 세트(`sandbox_type = quiz`), 문제 수는 29~31개. 전체 문제의 절반 이상이 이 세트들에 있다.
- 분야별: 도커 21, 리눅스 28, k8s 28, Git 14, 데이터베이스 6.
- 시험형(`time_limit_sec`)·`docker-persistent`·복습 세트(`is_review`)는 대상에 없다. 문제 수 11~25개 세트(실습 포함)는 이번에 건드리지 않는다.

## 원칙

- **대상**: 문제 수가 26개 이상인 `quiz` 세트. 퀴즈는 문제끼리 앞 문제의 상태에 기대지 않아서 중간에서 나눌 수 있다.
- **2개로 나눈다.** 문제 수 n 에 대해 앞 세트(1부)는 `ceil(n/2)` 개(15~16), 뒤 세트(2부)는 나머지(14~15)다. 최대 31개라 모두 2부로 충분하다.
- **문제 행은 새로 만들지 않고 옮긴다.** 2부로 가는 문제는 `quest.id` 를 그대로 두고 `quest_set_id` 와 `order_index`(1부터 다시)만 바꾼다. 그래서 문제 단위 시도 기록(`quest_attempt.quest_id`), 피드백의 문제 참조가 깨지지 않는다.
- **1부는 원래 세트 번호를 유지한다**(링크·완료 기록·북마크 호환). 2부는 새 번호를 받는다.
- 단원·분야·아이콘·공개 여부·샌드박스·설명은 1부와 같다. 2부는 같은 단원에서 1부 바로 뒤에 놓인다.
- 정답·해설은 서버가 갖는 구조 그대로다. 문제 내용은 바꾸지 않는다.

## 제목

- 1부 제목 = 원제목 + ` (1/2)`, 2부 제목 = 원제목 + ` (2/2)`.
- 제목이 92자를 넘는 세트가 17개라 접미사를 붙이면 `quest_set.title VARCHAR(100)` 을 넘는다. **칸을 `VARCHAR(200)` 으로 넓힌다** (`quest.title` 이 이미 200). 마이그레이션 `ALTER TABLE ... MODIFY` 는 여러 번 실행해도 안전하다.

## 번호와 순서

- 새 세트 번호는 238 부터, 원래 세트 번호 순으로 이어서 매긴다 (분야별로 나눠 진행해도 번호는 이어진다).
- `display_order`: 분야별로 **전체를 다시 매긴다.** (단원 순서, 단원 안 `display_order`, 세트 번호) 순으로 정렬해 그 분야의 현재 최솟값부터 1씩 올리며 절대값 `UPDATE` 로 적는다. 2부는 1부 바로 뒤다. 단원 안 세트가 이어지는 규칙([spec_units.md](spec_units.md))이 유지된다.

## 기존 데이터 처리 (결정)

| 대상 | 처리 | 이유 |
|---|---|---|
| `quest_attempt` | 옮긴 문제의 `quest_set_id` 를 새 세트 번호로 맞춘다 | 이어 풀기가 `(사용자, 세트, 세션)` 으로 찾는다. 2부 문제를 푼 중간 기록은 2부에서 이어진다 |
| `feedback` | 옮긴 문제를 가리키는 `quest_set_id` 를 맞춘다 | 피드백이 올바른 세트를 가리키게 |
| `set_completion` | **건드리지 않는다** | XP·랭킹·피드·연속 학습이 완료 기록으로 계산된다. 복제하면 XP 가 두 번 계산된다 |
| 이미 31문제를 끝낸 사용자 | 1부는 완료로 남고, 2부는 미완료로 보인다. XP 는 그대로다 | 완료 규칙을 바꾸지 않는다. 2부는 복습으로 풀 수 있고 처음 끝내는 것이라 XP 가 붙는다 (아래 열린 결정) |
| 풀던 중인 세션 | 1부 문제만 남은 세션은 1부에서 이어지고, 이미 1부를 모두 푼 세션은 이어 풀기 때 "모두 통과했는데 완료 기록 없음" 흐름으로 1부 완료가 저장된다 | [spec_resume_set.md](spec_resume_set.md) 5번 |
| `quest_set_access` | 옮기지 않는다 (현재 행 없음) | 0건. 생기면 2부에도 복사한다 |
| `backend/verify/quiz-proofs.json` | `(set, order)` 로 문제를 가리키므로 옮긴 문제는 새 세트 번호와 새 순번으로 바꾼다 | `verify:quiz` 가 깨지지 않게 |

## 반영 방식

- **생성 스크립트** `scripts/content-gen/split_quiz_sets.py <분야>`: 로컬 DB 에서 대상 세트를 읽어 SQL 과 `quiz-proofs.json` 변경을 만든다. 예시 생성기와 같이 직접 실행하는 도구이고, 이미 나눈 세트는 건너뛴다 (문제 수가 26 미만이므로).
- 새 DB(처음부터 만드는 경우): `backend/db/10_split_sets.sql`(신규, 번호가 09 뒤)에 분야별 SQL 을 이어 붙인다. `03_quest_setN.sql` 은 그대로 둔다 (`quest.id` 가 입력 순서로 정해지므로 파일을 고치면 번호가 달라진다).
- 이미 있는 DB: `backend/db/migrations/2026-11-12_split_quiz_sets_<분야>.sql` (분야별, 여러 번 실행해도 안전).
  - 2부 세트: `INSERT ... SELECT ... WHERE NOT EXISTS`
  - 문제 이동: `UPDATE quest SET quest_set_id = 새번호, order_index = order_index - m WHERE quest_set_id = 원번호 AND order_index > m` (다시 실행하면 대상 행이 없다)
  - 제목: `UPDATE ... SET title = CONCAT(title, ' (1/2)') WHERE id = 원번호 AND title NOT LIKE '% (1/2)'`
  - 기록 맞춤: `quest` 와 `quest_attempt`·`feedback` 을 조인해 `quest_set_id` 가 다른 행만 맞춘다.
  - `display_order`: 분야 전체 절대값 `UPDATE`.
- 분야별로 한 번에 하나씩 진행한다 (도커 → 리눅스 → k8s → Git → 데이터베이스). 분야마다 로컬 검증을 마치고 커밋을 나눈다.

## 하지 않는 것

- 실습(터미널) 세트와 11~25문제 세트 나누기. 퀴즈 분할 결과를 보고 이후 판단한다.
- 완료 규칙·XP 규칙 변경, 단계별 완료 보상(안 B).
- 문제 내용 수정, 주제별로 문제를 다시 묶기 (순서대로 반으로 나눈다).
- 1부·2부 사이에 "이어서 2부 풀기" 안내 화면. 단원 길에서 2부가 바로 다음 노드로 보이는 것으로 충분하다.

## 열린 결정 (기본안으로 진행)

| 결정 | 기본안 |
|---|---|
| 이미 끝낸 사용자의 2부 | 미완료로 둔다 (XP 규칙을 건드리지 않는 쪽). 불편하면 2부에 한해 1부 완료자를 완료로 보이게 하는 표시를 따로 명세한다 |
| 반으로 나누는 위치 | 문제 순서 그대로 `ceil(n/2)` (주제 경계는 보지 않는다) |
| 제목 접미사 | ` (1/2)`, ` (2/2)` |
