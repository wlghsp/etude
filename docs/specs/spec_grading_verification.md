# 채점 검증 러너 명세 — 채점이 맞다는 것을 자동으로 확인한다

> 상태: **V1, V2 구현 완료 (`linux`, `docker`, `docker-persistent`), V3 이후 대기** — 설계 결정은 "결정" 참고. [Phase 8d 명세](spec_phase8d_session_security.md)의 "범위 밖"에서 "퀘스트 채점식 전수 감사와 채점 검증 러너(다음 단계)"로 분리된 작업이다. 이 문서는 목표·결정·조각 분할만 다루고, 조각별 상세는 착수할 때 별도로 쓴다.

## 목표

모든 퀘스트에 대해 **정답을 수행하면 채점이 통과하고, 아무것도 하지 않으면 채점이 실패한다**는 것을 사람이 눈으로 보지 않고 자동으로 확인한다. 채점이 틀리면 학습자는 맞는 답을 하고도 막히거나, 틀린 상태로 통과해 신뢰를 잃는다.

## 현황 (코드와 콘텐츠로 확인한 사실)

- 채점은 컨테이너에서 `grade_cmd`를 실행해 **종료 코드 0이면 통과**로 본다 ([quest.ts](../../backend/src/services/quest.ts)의 `execCheck`, 타임아웃 15초는 실패 처리).
- 퀘스트는 14개 세트, 약 143개. 정의는 `backend/db/03_quest_set*.sql`이 유일한 출처다.
- 세트마다 샌드박스 타입이 다르다: `linux`, `linux-ssh`, `linux-systemd`, `docker`, `docker-persistent`, `k8s`(namespace 격리), `k8s-isolated` 등.
- 퀘스트는 `setup_cmd`(준비), `grade_cmd`(채점)를 가진다. 일부 세트는 앞 퀘스트의 상태가 뒤 퀘스트로 이어진다(`docker-persistent`).
- `solution` 필드는 **사람이 읽는 풀이 설명**이다. 실행 가능한 명령(`pwd > /tmp/pwd_result.txt`)도 있지만, 그렇지 않은 것도 있다(`vim /tmp/hello.txt 후 i → hello vim → ESC → :wq`). 그래서 `solution`을 그대로 실행해서는 검증할 수 없다.
- 자동 검증은 현재 없다. 콘텐츠를 고칠 때 사람이 직접 풀어 보는 것이 유일한 확인 방법이다.

## 검증 항목

퀘스트마다 같은 새 환경에서 다음을 확인한다.

| # | 검사 | 기대 | 잡아내는 문제 |
|---|------|------|---------------|
| 1 | **정답 통과**: `setup_cmd` → 정답 명령(oracle) → `grade_cmd` | 통과 | 채점식 오류, 정답인데 막히는 퀘스트 |
| 2 | **무행동 실패**: `setup_cmd`만 실행 → `grade_cmd` | 실패 | 아무것도 안 해도 통과하는 채점식 |

이 두 가지가 1차 범위다. "틀린 답이 통과하는가"(오답 oracle) 검사는 정의 비용이 커서 별도 조각으로 둔다.

## 설계

### 정답 명령(oracle)의 위치

실행 가능한 정답이 따로 있어야 한다. 위치 후보:

| 안 | 방식 | 장점 | 한계 |
|----|------|------|------|
| **A. DB 컬럼** | `quest` 테이블에 정답 명령 컬럼을 추가하고 `03_quest_set*.sql`에 함께 둔다 | 퀘스트 내용이 한 곳(SSOT) | 운영 DB 스키마 변경과 마이그레이션이 필요하고, 정답이 API/DB에 실린다 |
| **B. 검증용 fixture 파일** | `backend/verify/` 아래에 세트별 파일로 `(세트, order) → 정답 명령`을 둔다. 운영에는 올라가지 않는다 | 운영 변경 없음, 세트 단위로 점진 도입 | 퀘스트 수정 시 어긋날 수 있음 → 모든 퀘스트에 fixture가 있는지 검사하는 **커버리지 검사**로 막는다 |

### 추천: B

운영 스키마를 건드리지 않고 세트별로 점진 도입할 수 있고, 어긋남은 커버리지 검사(fixture 없는 퀘스트, 퀘스트 없는 fixture를 실패로 보고)가 잡는다. 정답은 학습자에게 노출되는 `solution`과 용도가 다르다는 점도 분리를 정당화한다.

### 실행 방식

- 러너는 **개발자가 로컬에서 실행하는 도구**다 (`npm run verify:quests -- --set <id>`). 실제 Docker가 필요해 `vitest`의 일반 테스트와 섞지 않는다.
- 퀘스트 목록과 `setup_cmd`/`grade_cmd`는 **DB에서 읽는다**(로컬 개발 DB). SQL 파일을 직접 파싱하지 않는다(취약).
- 컨테이너는 서비스 코드의 샌드박스 설정(`getSandboxConfig`)을 그대로 따라 만든다. 같은 이미지·binds·권한으로 검증해야 결과가 실제와 같다.
- 상태가 이어지는 세트(`docker-persistent`)는 한 컨테이너에서 순서대로 진행하고, 무행동 검사는 각 퀘스트 시작 시점의 상태에서 실행한다.
- 결과는 퀘스트별 `통과/실패 + 사유`와 요약으로 출력하고, 실패가 하나라도 있으면 종료 코드가 0이 아니다.

### 조각 분할

타입별로 환경 비용이 크게 달라 한 번에 하지 않는다.

| 조각 | 범위 | 비고 |
|------|------|------|
| **V1. 러너 뼈대 + `linux` 세트** | fixture 형식, 커버리지 검사, 정답/무행동 검사, `linux` 타입 세트(1, 2, 3, 7, 9) | 가장 환경이 단순. 여기서 러너 설계를 확정한다 |
| **V2. `docker` / `docker-persistent`** | 세트 5, 8, 11 | Docker-in-Docker와 상태 이어짐 처리 |
| **V3. `linux-systemd` / `linux-ssh`** | 세트 10, 4 | systemd 기동 대기, ssh 대상 필요 |
| **V4. `k8s`** | 세트 6, 12, 13, 14 | 실제 클러스터 필요, 가장 무거움 |
| **V5. 오답 검사** | 채점식이 느슨한 퀘스트에 "틀린 답"을 정의하고 통과하지 않는지 확인 | 효과는 크지만 정의 비용이 큼. V1~V4에서 발견한 취약 채점식 우선 |

참고:
- 7.7~7.9는 **이미지 결함**이라 코드/콘텐츠가 아니라 이미지를 고쳐야 한다. 서버에도 재빌드한 이미지를 반영해야 한다.

- fixture는 `solution`에서 초안을 만든 뒤 독립 파일로 관리한다. 실행 불가능한 풀이(세트 9 전체, 3.3, 3.7)는 같은 최종 상태를 만드는 비대화형 명령(`sed` 등)으로 직접 썼다.

## V2 결과 (2026-10-28, `docker`/`docker-persistent` 세트 5, 8, 11 — 26개 중 23 통과, 3 실패 → 수정 후 26 통과, 0 실패)

| 퀘스트 | 판정 | 원인 | 수정 |
|--------|------|------|------|
| 5.7 컨테이너 중지하기 | 무행동 통과 | 채점식 `docker ps \| grep -qv my-nginx`의 `-v`는 "my-nginx가 *없는* 줄이 하나라도 있으면 성공"이다. 헤더 줄 때문에 컨테이너가 떠 있어도 통과 | `! docker ps \| grep -q my-nginx` |
| 8.6 레지스트리에 이미지 올리기 | 정답 거부 | 채점식이 `curl`을 쓰는데 `docker:dind` 이미지에는 `curl`이 없다 (`wget`만 있음). 학습자가 정답을 해도 영원히 실패 | `wget -qO-`로 교체 |
| 8.7 레지스트리에서 받아 실행하기 | 무행동 통과 | 채점식이 8.5와 같아, 앞 퀘스트를 풀었다면 풀기 전에 이미 통과 | 실행 결과를 `/tmp/run_result.txt`에 저장하게 하고 그 파일을 채점 |

- 수정은 원본 SQL과 [update_2026-10-28_grading_fixes_docker.sql](../../backend/db/update_2026-10-28_grading_fixes_docker.sql)에 함께 반영했다. **서버 DB에는 이 파일을 한 번 실행해야 반영된다.**
- 세트 8(`docker-persistent`)은 퀘스트 사이에 상태가 이어져 한 컨테이너에서 순서대로 검증한다 (`runPersistentSet`: 풀기 전 채점 → 정답 → 채점). 이 방식이라 8.7처럼 *앞 퀘스트 때문에* 통과하는 결함까지 잡힌다.
- `docker` 계열 샌드박스는 실제 앱(`handleDockerTerminal`)과 같이 Privileged dind로 만들고, 앱이 소켓 존재만 기다리는 것과 달리 `docker info`가 성공할 때까지 기다린다 (검증의 오탐을 줄이기 위함이며, 실제 앱의 기동 직후 경쟁 상태는 이 검증이 보지 않는다).
- 세트 5와 11은 퀘스트마다 새 dind를 띄워 느리다 (세트 5, 8 합쳐 약 3분, 세트 5, 11 합쳐 약 4분).
- 앱은 상태가 이어지는 세트에서 첫 퀘스트의 `setup_cmd`만 실행한다 (재접속이 없어져 이후 퀘스트의 setup은 실행되지 않음). 세트 8은 `setup_cmd`가 없어 영향이 없다. 러너는 퀘스트마다 setup을 실행하므로, 이후 `setup_cmd`가 있는 persistent 세트가 생기면 이 차이를 다시 봐야 한다.
