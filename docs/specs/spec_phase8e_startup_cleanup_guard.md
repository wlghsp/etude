# Phase 8e 명세 — 기동 정리 보호 장치 (중복 실행 방지)

> 상태: **구현 완료 (안 A)** — 설계 결정은 아래 "결정" 참고. [Phase 8d 명세](spec_phase8d_session_security.md)의 "범위 밖"에서 분리된 작업이다.

## 목표

backend가 이미 실행 중일 때 두 번째 프로세스가 기동하면서 **기존 프로세스의 실습 컨테이너·vcluster pool·kubeconfig를 지우는 일**을 막는다.

## 현황 (코드로 확인한 사실)

[index.ts](../../backend/src/index.ts)의 기동 순서:

```
cleanupOrphanContainers()        ← etude=sandbox 라벨 컨테이너 전부 stop/remove
cleanupOrphanQuestNamespaces()   ← quest- 네임스페이스 정리
initPool()                       ← cleanupOrphanVclusters() (vcluster 전부 + pool kubeconfig 삭제) 후 pool 생성
buildApp() → listen(3001)        ← 여기서 비로소 포트 충돌(EADDRINUSE)
```

두 번째 프로세스는 포트 충돌로 죽기 전에 이미 파괴적 정리를 끝낸다. 결과: 첫 번째 프로세스의 **접속 중인 사용자 세션이 컨테이너를 잃고**, pool의 vcluster와 8d에서 정리 대상이 된 kubeconfig 파일도 사라진다. 첫 번째 프로세스의 메모리(세션 레지스트리, pool 배열)는 그대로라 서로 어긋난 상태가 된다.

발생 경로: 개발 중 `npm run dev`를 두 번 실행, 재시작 스크립트 오작동, 배포 중 구·신 프로세스가 겹치는 구간.

## 설계 선택지

| 안 | 방식 | 장점 | 한계 |
|----|------|------|------|
| **A. 포트 선점 확인** | 정리 전에 `net.createServer().listen(PORT)`로 포트를 잡아 본다. `EADDRINUSE`면 정리 없이 종료. 성공하면 닫고 정상 기동 | 코드 몇 줄, 상태 파일 없음, 같은 포트를 쓰는 모든 중복을 막음 | 확인과 실제 `listen` 사이에 짧은 틈(TOCTOU). **서로 다른 포트/컨테이너가 같은 Docker 데몬을 공유하면 못 막음** |
| **B. listen 먼저** | `listen`을 정리보다 앞에 둔다. 정리 중에는 요청을 받지 않도록 준비 완료 플래그가 필요 | 틈이 없음 | 정리 전에 들어온 요청이 정리에 지워질 수 있어 준비 게이트(503)가 추가로 필요. 변경이 큼 |
| **C. 락 파일** | `~/.etude/backend.lock`에 PID를 쓰고, 살아 있는 PID면 종료 | 포트와 무관 | 컨테이너 배포에서는 파일이 공유되지 않아 효과가 없을 수 있고, 비정상 종료 후 stale 락 처리가 필요 |

### 추천: A

가장 흔한 사고(같은 호스트·같은 포트에서 이중 실행)를 최소 변경으로 막는다. 틈은 의도적인 동시 기동이 아닌 이상 실무상 문제가 되지 않는다. 한계(다른 포트로 같은 Docker 데몬을 공유)는 이 Phase에서 막지 않고 문서에 명시한다.

## 결정

1. **안 A(포트 선점 확인)를 채택**한다.
2. 포트 선점 확인에 실패하면 **정리 없이 즉시 종료(exit 1)**하고, 로그에 "이미 실행 중이라 기동을 중단한다"를 남긴다.

## 수용 조건 (A 기준)

- [x] 포트가 이미 사용 중이면 `cleanupOrphanContainers`, `cleanupOrphanQuestNamespaces`, `initPool`(= `cleanupOrphanVclusters`)이 **하나도 호출되지 않고** 프로세스가 비정상 종료한다
- [x] 포트가 비어 있으면 기존 순서대로 정리 후 기동한다
- [x] 선점 확인에 쓴 임시 서버는 확인 직후 닫힌다 (이후 실제 `listen`이 성공한다)
- [x] 종료 시 사유가 로그에 남는다

## 테스트 전략

- 포트 선점 확인 함수를 `index.ts`에서 분리해 단위 테스트한다: 임의 포트를 먼저 점유한 상태에서 `EADDRINUSE`를 보고하는지, 비어 있으면 통과하고 포트를 해제하는지
- 기동 순서(확인 → 정리 → pool → listen)는 `index.ts`가 최상위 `await`로 바로 실행되는 구조라 단위 테스트가 어렵다. 순서는 코드 리뷰로 확인하고, 필요하면 기동 로직을 함수로 분리하는 리팩터링을 별도 조각으로 둔다

## 범위 밖

- 다중 backend 인스턴스 운영 (세션 레지스트리가 메모리라 8d 명세상 지원하지 않음)
- 같은 Docker 데몬을 공유하는 서로 다른 포트의 이중 실행 방지
- 정리 로직 자체의 변경 (무엇을 지울지는 그대로)

## 구현 순서

1. 포트 선점 확인 함수: 단위 테스트 → 구현
2. `index.ts` 기동 순서에 연결 (정리보다 앞)
3. 문서 반영 (`docs/ops/`의 서버 운영 가이드에 "이중 실행 시 동작" 한 줄)
