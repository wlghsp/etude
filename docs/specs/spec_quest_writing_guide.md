# 퀘스트 문구 작성 기준

> 상태: 기준 확정(2026-10-29), 세트 19에 먼저 적용. 나머지 세트는 사용자 확인 후 순서대로 적용한다. 계기: "설명이 불친절하다, 제목이 와닿지 않는다"는 피드백.

## 원칙

학습자는 이 명령을 처음 본다고 가정한다. **무엇을, 어디에, 어떤 이름으로** 해야 하는지 설명만 읽고 알 수 있어야 하고, 힌트는 "형태"를, 풀이는 "왜"를 알려 준다.

## 제목

- **하는 일을 동사로 쓴다.** 도구 이름이나 개념어만 쓰지 않는다. 예: ~~YAML 을 뽑아 고쳐서 적용하기~~ → "Deployment YAML 을 만들어 저장하고 적용하기"
- 한 줄로 읽혀야 한다. 설명을 안 읽어도 무엇을 하는 문제인지 짐작되면 좋다.

## 설명

순서: **왜 필요한가(한두 문장) → 할 일(번호 목록, 구체적 이름·값) → 완료 조건**.

- 이름, 이미지, 파일 경로, 값은 `백틱`으로 감싸 본문과 구분한다 (화면에서 코드 모양으로 보인다).
- "A 를 B 에 저장한 뒤 C 에 적용하세요"처럼 한 문장에 여러 동작을 넣지 않는다. 단계를 나눠 번호를 붙인다.
- 어떤 네임스페이스·파일·이름을 쓰는지 빠뜨리지 않는다. 이미 만들어져 있는 것(setup)과 직접 만들 것을 구분해서 쓴다.
- 채점이 보는 것을 "완료 조건"으로 밝힌다 (예: "클러스터에 web Pod 는 없어야 합니다").

## 옵션 설명 (필수)

명령에 쓰는 **모든 옵션과 기호는 의미를 한 줄로 풀어 쓴다.** 힌트에서는 "어떤 옵션이 무슨 뜻인지"를, 풀이에서는 `#` 주석으로 "왜 이 옵션을 썼는지"를 적는다. 예: `-r` 은 디렉토리 안까지 재귀적으로, `-p` 는 없는 중간 디렉토리까지, `2>&1` 은 에러를 정상 출력과 같은 곳으로. 옵션 설명이 빠지면 정답을 봐도 왜 그렇게 쓰는지 알 수 없다. (사용자 요청, 2026-10-29)

## 힌트

- 정답 명령을 그대로 알려 주지 않고 **형태**를 보여 준다: `kubectl run <이름> --image=<이미지> ...`
- 각 옵션이 무슨 뜻인지 한 줄씩 풀어 쓴다. 확인 방법(`get`, `cat` 등)을 함께 쓴다.

## 풀이

- 실제로 입력할 명령 + `#` 주석으로 "왜 이렇게 하는지" 한 줄. 여러 단계는 단계마다 주석.
- 풀이는 화면에 고정폭 글꼴로 표시되고, 검증 러너가 쓰는 정답(`backend/verify/setNN.json`)과는 별개다 (표시용이므로 주석을 넣어도 채점에는 영향이 없다).

## 반영 방법

원본(`backend/db/03_quest_set*.sql`)과 이미 배포된 DB를 함께 고친다: 원본을 고치고, 같은 내용의 `UPDATE`를 `backend/db/migrations/`에 새 파일로 추가한다 ([guide_db_migrations.md](../ops/guide_db_migrations.md)). 채점 조건은 바꾸지 않는다.
