# 세트 513·514 문제 텍스트 점검 (review_D)

정답·복수 정답·MariaDB 10.6 사실(EXPLAIN 열 순서 type=4/rows=9, binlog_expire_logs_seconds(10.6.1+), PURGE TO 의미, 오류 번호 1045/1205/1040/1062/1032, KILL QUERY, sql_slave_skip_counter, FLUSH PRIVILEGES 후 ALTER USER)는 모두 이상 없음. 객관식 정답 index, fill answer_spec, order answer_spec 모두 사실과 일치. 순서 문제 513:12, 514:6 은 순서가 하나로 고정됨. 현장 정보(IP·도메인·내부 이름) 없음(127.0.0.1·테스트 비밀번호만).

## 차단

513:6 — description 이 저장할 값의 형식을 모호하게 둠. "원래 의도한 `64M`" 이라 적혀 있어 `64M` 을 그대로 쓰기 쉬운데, 채점은 서버 값 `67108864`(바이트).
  수정안 description =
  연습용 MariaDB 서버(설정 `/tmp/lab/my.cnf`, 소켓 `/tmp/lab/mysql.sock`)가 뜨지 않고 바로 종료됩니다. 서버는 `mariadbd --defaults-file=/tmp/lab/my.cnf` 로 띄우며, 서버가 남긴 **에러 로그는 `/tmp/lab/error.log`** 입니다.

  에러 로그에서 원인을 찾아 설정 파일을 고치고, 서버를 띄우세요. 서버가 떠 있는 상태에서 서버가 실제로 쓰는 `innodb_buffer_pool_size` 값(원래 의도한 `64M`)을 **바이트 단위 숫자**로 `/tmp/bp.txt` 에 저장하세요. (값만)

  (서버는 `nohup mariadbd ... &` 처럼 백그라운드로 띄웁니다. 접속은 `mariadb -S /tmp/lab/mysql.sock` 입니다.)
  (checks 라벨 "저장한 값이 64M 다" 도 "저장한 값이 64M(67108864) 다" 로 맞추면 좋음)

## 권고

513:12 — hint 가 순서 전체(파악, 급한 불 끄기, 원인 분석, 수리, 확인)를 그대로 나열해 누설.
  hint = 서비스가 지금 겪는 피해를 줄이는 일과 원인을 파고드는 일 중 무엇이 먼저인지 생각해 보세요. 고친 뒤에는 잘 고쳐졌는지 보는 일이 따릅니다.

513:3 — title 의 "전체를 훑고 있다" 와 description 의 "`ALL` 은 테이블 전체 훑기" 가 type=ALL 정답을 사실상 알려 줌.
  title = EXPLAIN 으로 실행 계획 읽기
  description = 폭주한 원인은 `shop` 의 `orders` 테이블(주문 30만 건)에서 고객별로 조회하는 쿼리가 느린 것이었습니다. 이 쿼리가 어떻게 실행되는지 `EXPLAIN` 으로 확인하세요.

  `SELECT * FROM orders WHERE customer_id = 77` 의 실행 계획에서 다음 두 값을 파일에 저장하세요. (값만)
  - `/tmp/type.txt` : `type` 열 (접근 방식)
  - `/tmp/rows.txt` : `rows` 열 (읽을 것으로 예상한 행 수)

514:10 — hint 가 "복제본에 있나, 없나" 로 두 보기의 답을 그대로 풀어 줌.
  hint = `1062` 는 `Duplicate entry`, `1032` 는 `Can't find record` 라는 영어 메시지로 나옵니다. 각 메시지가 "복제본의 데이터가 어떤 상태일 때" 나올 말인지 풀어 보세요.

514:12 — hint 가 skip 개수 값(1)을 알려 주고 "문제 한 건"은 퀴즈 문제로 읽혀 어색함.
  hint = 복제를 멈춘 상태에서 "다음에 건너뛸 이벤트 그룹 수"를 정하는 서버 변수를 쓰고 다시 시작합니다. 건너뛴 뒤에는 상태 필드와 두 서버의 `items` 를 비교해 같은지 확인하세요.

514:2 — hint 가 "시간 순서로 어느 쪽이 먼저" 라며 정답(첫 줄)을 거의 지목.
  hint = `[ERROR]` 가 여러 줄이면 원인과 그 여파가 섞여 있습니다. 어느 줄 하나를 고치면 나머지가 저절로 사라질지 생각해 보세요.

514:6 — hint 가 마지막 두 단계("끝나면 되돌리고, 마지막에 결과를 확인")와 가운데 단계까지 서술.
  hint = 보안 검사를 끄는 구간은 짧을수록 좋습니다. 서버를 내렸다 올리는 사이에 무엇을 하고, 끝난 뒤 무엇을 되돌려야 하는지 떠올려 보세요.

## 참고 (수정 불필수)

514:1 — description "행 수(3)" 가 n.txt 값을 알려 줌(채점이 서버 기동·소유자도 함께 보므로 통과 불가 우회는 아님). 필요하면 "행 수를 `/tmp/n.txt` 에 저장하세요" 로.
514:1·514:2 — 로그 문구 `The data file './ibdata1' must be writable` 은 예시. MariaDB 10.6 실제 문구가 `The innodb_system data file ...` 일 수 있어 미검증(샌드박스 로그와 대조 권장). 오류 줄 순서도 실제와 다를 수 있음.
514:1 hint/description 이 원인(소유자 변경)을 미리 알려 "로그에서 원인 찾기" 성격이 약함. 의도된 시나리오면 유지.
514:4·5·6 — 옵션 설명이 4번 description 에 이미 있어 5번 빈칸·6번 순서가 복습형(같은 사실 반복). 복제는 아님.
514:2 — 정답 보기(마지막 보기)가 길고 "나머지는 그 여파" 를 스스로 설명해 오답보다 눈에 띔(보기 수정 불가라 참고만).
513:11 — template 에 Rows_sent·Lock_time 이 이미 있어 그 두 보기는 소거됨. 사실 오류는 아님.
513·514 전 문제의 docs 링크가 세트 공통이라 일부 문제와 무관(예: 513 의 PURGE BINARY LOGS 링크를 EXPLAIN 문제에 표시).
513:10 hint 가 "No space left" 에 주목하라 해 정답을 거의 알려 주나, description 에 이미 같은 문구가 있어 수준은 동일.
