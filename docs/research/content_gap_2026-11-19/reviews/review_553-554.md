## 권고

### R1. 553:4·553:6 — 이미지 크기를 `Size`(inspect)로 재면 containerd 이미지 저장소에서 고치지 않아도 통과한다 (검증됨, 로컬 도커)
- 553:4 의 `SMALL('t4')` 는 `docker image inspect -f '{{.Size}}'` 를 쓴다. 이 도커는 containerd 스냅샷터(`io.containerd.snapshotter.v1`)를 쓰고, 이 경우 `Size` 는 압축된 콘텐츠 크기다. 로컬에서 `alpine:3.19` 가 3.37MB(압축)로 나오고, **고치지 않은 원본 Dockerfile 로 빌드한 t4 가 3.39MB** 였다. `dd if=/dev/zero` 30MB 는 압축하면 수십 KB 라서 크기 검사를 그냥 통과한다. `docker history` 로는 같은 이미지가 31.5MB 레이어로 보인다(비압축).
- 결과: 553:4 는 "고치지 않고 `docker run --rm t4 > /tmp/q4.txt` 만 해도" 통과할 수 있다(체크 2개 모두 충족). 무행동 실패는 지키지만 "고쳤는지"를 못 가린다. 553:6 은 `/opt/toolchain.bin` 부재 검사가 따로 있어 안전하고, `SMALL` 만 의미가 약해진다.
- 샌드박스(dind) 도커가 overlay2 클래식 저장소면 지금도 동작한다. 샌드박스 이미지의 저장소 종류에 따라 갈리므로 **미검증·추정**이다. 도커 엔진 버전이 올라가면 바뀔 수 있어 방어적으로 고치는 편이 안전하다.
- 수정안: 크기 대신 레이어 구성으로 판정한다. 예) t4 의 `docker history --no-trunc --format '{{.Size}} {{.CreatedBy}}' t4` 에서 "pkg.tmp 를 만든 레이어 줄에 `rm -f /var/cache/pkg.tmp`(또는 `rm`)가 같이 들어 있다" 를 `docker history --no-trunc t4 | grep 'dd if=/dev/zero of=/var/cache/pkg.tmp.*rm '` 식으로 검사. 또는 `docker history --format '{{.Size}}'` 의 MB 단위 값 중 5MB 를 넘는 레이어가 alpine 기본 레이어(약 8MB)뿐인지 보는 방식. 553:6 도 `SMALL` 대신 같은 방식(또는 기존 `toolchain.bin` 부재 검사만 유지)으로.
- 부수 효과: 설명이 "이미지가 크면 받는 시간·디스크가 늘어난다"고 하는데, 0 으로 채운 파일은 압축 전송 크기에는 거의 반영되지 않는다(아래 "dd 흉내 방식" 참고).

### R2. 554:4 — `die` 횟수 = `RestartCount + 1` 검사가 재시도·재진입 시 깨질 수 있다
- 채점은 `docker events --since 10m`(학습자 명령)로 저장한 줄 수가 `RestartCount + 1` 과 같은지 본다. 필터가 `container=flap`(이름)이라, 같은 샌드박스에서 이 문제의 setup 이 10분 안에 다시 실행되면(문제 다시 열기·재채점·`verify:quests` 두 번 연속) **이전 `flap` 컨테이너의 `die` 사건까지 함께 잡혀** 줄 수가 8, 12 … 가 되어 정답을 내도 실패한다. (`CLEAN` 은 컨테이너만 지우고 이벤트 기록은 못 지운다.) 샌드박스가 매번 새 데몬이면 문제 없다 — **미검증·추정**.
- 수정안: 두 번째 검사를 `-ge` 로 완화하고 하한을 둔다. 예) `[ "$(wc -l < /tmp/q4.txt)" -ge "$(( $(docker inspect -f {{.RestartCount}} flap) + 1 ))" ]`. 정확한 일치를 유지하려면 setup 마지막에 현재 시각을 `/tmp/.q4t` 에 적어 두고 설명에서 `--since` 를 그 시각으로 쓰게 하는 방법도 있으나 문제가 복잡해진다. 완화가 간단하다.

### R3. 554:10 — 순서 문제가 "설명에 순서를 다 적어 줘서" 판단할 것이 없고, 해설의 "로그를 가장 나중에" 주장이 약하다
- description 이 정답 순서(상태 → 횟수 → 시점 → 원인)를 그대로 적고 카드마다 "상태/횟수/시점/원인" 단어가 들어 있다(`상태(Restarting 등)`, `재시작 횟수`, `종료·재시작 시점`, `원인을 찾는다`). 순서가 하나로 고정되는 점은 기준을 충족하지만, 카드의 단어를 설명 단어와 짝짓기만 하면 되어 학습 가치가 낮다. README 기준 5(순서 문제 힌트는 순서를 나열하지 않는다)의 취지에 어긋난다. 힌트도 "단계 이름에 짝지어 보세요"로 사실상 같은 말이다.
- 해설 "원인은 컨테이너 안에서 나므로 로그를 가장 나중에 읽는 것이 효율적" 은 현장에서 로그를 먼저 보는 경우가 많아 단정으로 읽힌다.
- 수정안(택1): (a) description 에서 순서 나열을 빼고 "넓은 것에서 좁은 것으로: 문제가 있는지 → 얼마나 반복되는지 → 언제부터인지 → 왜인지" 정도의 기준만 주고, 카드의 단어(`상태`, `횟수`, `시점`, `원인`)는 줄인다. 해설은 "범위를 좁혀 가는 흐름"으로 바꾸고 "가장 효율적" 단정은 뺀다. (b) 그대로 두고 해설만 순화. 최소한 (b)는 권고.

### R4. 553:6 — "두 단계로 바꿔" 라고 했는데 채점이 멀티 스테이지를 요구하지 않는다
- 채점은 결과 `built-app`, `/opt/toolchain.bin` 부재, 크기 세 가지다. 한 단계 Dockerfile 에서 `RUN dd ... && echo ... && rm /opt/toolchain.bin` 로 같은 RUN 안에서 지우거나 dd 줄을 없애도 통과한다(R1 때문에 크기 검사는 더 느슨). 문제 제목이 "멀티 스테이지" 이므로 의도와 채점이 어긋난다.
- 수정안: `chk('Dockerfile 이 두 단계 이상이다', '[ "$(grep -ci "^FROM" /tmp/work/q6/Dockerfile)" -ge 2 ] && grep -q "COPY --from" /tmp/work/q6/Dockerfile')` 추가. (553:4 는 반대로 "같은 RUN 에서 지우기"가 목적이라 다양한 해법 허용이 맞다.)

### R5. 553:8 — 출력만 맞으면 `/data` 를 쓰지 않아도 통과
- 설명은 "`app` 이 `/data` 에 쓸 수 있어야" 라고 하는데, 채점은 출력 `saved` 와 `Config.User=app` 뿐이다. CMD 를 `/tmp` 에 쓰도록 바꾸거나 `echo saved` 로 바꿔도 통과한다(무행동은 막힘).
- 수정안: `docker run --rm t8 sh -c 'cat /data/out.txt'` 가 아니라, `docker run --rm --entrypoint sh t8 -c 'touch /data/x'` 가 성공하는지 보는 검사를 추가("`app` 으로 `/data` 에 쓸 수 있다"). `Config.User` 검사는 유지.

## "dd 로 큰 파일을 흉내 낸 방식"이 학습 오해를 만드는가

- 대체로 **괜찮다**. 목적이 "레이어에 들어간 파일은 이후 레이어에서 지워도 남는다", "멀티 스테이지로 빌드 도구를 최종 이미지에서 뺀다", "history 로 큰 레이어를 찾는다" 라는 구조 학습이고, 설명이 "`dd` 로 흉내 낸 것, 실제로는 `apt-get install` 뒤 `rm -rf /var/lib/apt/lists/*`, alpine 은 `apk add --no-cache`" 라고 밝혀 두었다. 흉내라는 점과 실제 명령이 함께 제시돼 오해 위험이 작다.
- 남는 위험 두 가지(권고 R1 과 연결):
  1. 0 으로 채운 파일은 압축률이 매우 높아 **받는 시간·레지스트리 전송량**에는 거의 반영되지 않는다. 설명의 "받는 시간·디스크가 늘어난다"를 이 흉내로 체감하긴 어렵고, 크기를 압축 콘텐츠 크기로 보는 도커에서는 크기 자체가 안 늘어난다. 채점·설명 모두 "레이어(비압축) 크기" 기준으로 쓰는 것이 일관적이다. 해결안은 R1 + 설명에 "크기는 압축 전 레이어 크기 기준" 한 줄.
  2. 학습자가 `dd` 줄을 "패키지 설치의 대체"가 아니라 "원래 쓰는 명령"으로 오해하지 않도록, 553:4·6 의 문장 그대로 "설치를 흉내 낸 줄" 이라는 안내를 유지한다(이미 있음). 추가 조치 불필요.
- 대안(선택): 큰 파일을 `head -c 30M /dev/urandom` 으로 만들면 압축이 안 되어 전송 크기·`Size` 모두 늘어나지만, 이미지 빌드 시간·미러 용량이 늘어난다. 이번 범위에서는 R1 의 히스토리 검사가 더 싸다.
