## 차단

- 525:13 — 순서 문제가 하나로 고정되지 않는다. "엔티티 찾기 → 속성·PK 정하기 → 관계 판단" 에서 속성·PK 와 관계 판단은 교재에 따라 순서가 반대(엔티티 → 관계 → 속성)로도 쓰이므로 `[2,4,1,0,3]` 도 정당한 답이다. 수정안: `description` 끝에 "이 문제에서는 각 테이블의 열과 기본키를 먼저 정한 뒤 관계를 판단합니다." 를 추가해 순서를 고정한다. 아울러 `hint` 를 "각 단계는 앞 단계의 결과를 입력으로 씁니다. 외래 키는 부모의 기본키가 정해져야 걸 수 있습니다." 로 바꾼다(현재 힌트는 순서를 거의 그대로 나열한다).

## 참고

- 522:7 → 522:8 — 522:7 `description` 에 "NOT EXISTS" 가 그대로 나와 522:8 빈칸이 사실상 복습이다. 조치 불필요(복습 의도로 허용 가능).
- 522:10 — `hint` 가 두 해법(NOT EXISTS / IS NOT NULL)을 모두 알려 준다. 학습 목적상 허용.
- 523:4 — `description` 괄호 설명("공동 순위 수만큼 다음 순위를 건너뜁니다")만으로 답이 나온다. 쉬운 문제로 유지하는 설계라면 그대로 둔다.
- 523:10 — LAG 는 `description` 에서 정의를 주므로 문맥 밖은 아니다. 문제 없음.
- 524:3, 524:12, 525:4, 525:12, 527:9, 527:12 — 정답 보기가 가장 길고 구체적이다(길이 단서). 오답 보기도 비슷한 길이·구체성으로 맞추면 더 좋다.
- 524:4 — 채점이 `0` 출력과 `Com_prepare_sql` 증가만 본다. `PREPARE` 후 `SELECT 0` 으로도 통과할 수 있으나 학습 의도상 허용 가능.
- 524:8 — "authentication_string 이 비어 있으면 비밀번호 없음" 은 `unix_socket` 처럼 비밀번호를 쓰지 않는 인증 플러그인 계정에도 해당하므로 엄밀히는 단순화다. 해설에 한 줄 추가하면 좋다.
- 525:3 vs 525:7 — `customers` 열이 다르다(525:3 은 id·name·email, 525:7 setup 은 id·name). 문제마다 환경이 독립이라 동작에는 문제 없다.
- 525:11 — 채점이 3줄·kim-linux·lee 만 sql 만 확인하고 kim-sql 은 보지 않는다. 필요하면 `kim sql` 확인 check 추가.
- 525:12 — `description` "양쪽이 모두 `{` 로 끝나면 양쪽이 여러 개입니다" 는 `}o--o{` 표기와 맞지 않는 표현이다. "`{` 가 있는 쪽은 여러 개" 로 고치면 정확하다.
- 526:8 — `description` 은 "customers 에 있으므로" 라고 하지만 이 문제 환경(setup)에는 `customers` 가 없다. "(앞 문제에서 만든) customers" 로 표현을 맞추면 혼동이 없다. 채점도 6행·열 없음만 봐서 `order_id` 기본키·`customer_id`·`product`·`price` 열 확인을 더하면 좋다.
- 526:9 — 채점이 6번 행과 정렬만 본다. 1번 행(`1 kim Seoul keyboard 30000`) check 를 더하면 열 순서 오류까지 잡는다.
- 526:10 — 보기에 1NF/2NF/3NF 가 적혀 있어 거의 자명한 순서 문제다. 단계의 설명을 보고 풀게 하려면 보기에서 번호를 빼는 방법이 있다(선택).
- 527:4 — 해설의 GETEX 는 Redis 6.2 이상 명령이다. 샌드박스 Redis(Ubuntu 22.04 패키지 6.0.x)에는 없으므로 실행해 보라는 안내는 하지 말 것(보기 설명으로만 사용 중이라 현재는 문제 없음).
- 527:8 — `SET ... NX` 를 쓰지 않고 `EX` 만으로도 `OK` 가 나와 통과한다(NX 사용 여부 미검증). 학습 의도상 허용.
- 527:5 — `KEEPTTL` 은 Redis 6.0 이상. 샌드박스 6.0.x 에서 지원되므로 문제 없다.
