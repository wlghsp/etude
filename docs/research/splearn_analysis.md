# 분석: `splearn` (토비의 스프링 부트 강의 실습, Java/헥사고날)

분석 대상: `/Users/jihochoi/Documents/study/tobyspring/splearn`

목적: Etude의 Kotlin 백엔드 마이그레이션(Phase 12)에 참고할 만한 패턴을 뽑아낸다. 이미 두 프로젝트를
분석했다 — 우아한형제들 `service-apply`(Kotlin/DDD, [woowacourse_service_apply_analysis.md](woowacourse_service_apply_analysis.md)),
`cafekiosk`(Java/TDD, [cafekiosk_analysis.md](cafekiosk_analysis.md)). `splearn`은 그 둘과 달리
**문서화 산출물**(용어사전, 도메인 모델 문서, 다이어그램)이 리포 루트에 그대로 남아있는 학습용
프로젝트라, 이번 분석은 그 부분에 분량을 집중한다 — Etude가 아직 정식 용어사전이나 도메인 모델
다이어그램을 갖고 있지 않기 때문이다.

## 1. 문서화 산출물 — 이 분석의 핵심

리포 **루트**에 4개의 한국어 문서가 코드와 나란히 있다: `용어사전.md`, `도메인모델.md`,
`도메인모델.drawio`, `개발가이드.md`. `docs/` 서브폴더가 아니라 루트에 바로 두고, 파일명 자체가
한국어라는 점부터 특징적이다.

### 1-1. `용어사전.md` — 3열 표, 매우 얇음

전체 11줄, 마크다운 테이블 하나가 전부다.

```
| **한국어** | **영어**         | **설명**                                     |
| ------- | -------------- | ------------------------------------------ |
| 회원      | Member         | 스프런 서비스를 이용하는 사용자로 강의를 수강할 수 있다            |
| 강사      | Instructor     | 강의를 만들고 제공하는 회원. 회원은 신청 과정을 통해서 강사가 될 수 있다 |
```

한국어-영어-설명 3열로, 도메인 용어와 코드의 클래스/필드명(영어)을 1:1로 매핑하는 게 유일한
목적이다. 분류나 예시, 관련 개념 링크는 없다. `도메인모델.md`에 "1. 듣고 배우기 → 2. '중요한 것'들
찾기(개념 식별)"라는 프로세스가 명시되어 있어, 용어사전은 그 2단계의 산출물 — 즉 완성형 사전이
아니라 **도메인 모델링 워크숍 중간 산출물**로 보인다.

### 1-2. `도메인모델.md` — 서술형 요구사항 + 구조화된 모델 정의가 한 문서에 공존

가장 핵심적인 문서다. 두 부분으로 나뉜다.

**(1) 도메인 스토리(자연어 서술)**: "스프런은 회원이 강의를 수강하는 온라인 서비스이다... 등록
신청을 한 뒤 정해진 요건을 충족하면 등록이 완료된다... 프로필 주소는 알파벳과 숫자로 구성된
15자리 이내의 중복되지 않은 값"처럼 비즈니스 규칙을 문단으로 기술한다.

**(2) 구조화된 모델 정의**: 애그리게잇별로 고정된 템플릿(`속성` / `행위` / `규칙`)을 쓴다.

```
### 회원(Member)
_Aggregate Root_
#### 속성
- `id`: `Long`
- `email`: `Email` - Natural ID
- `status`: `MemberStatus` 회원 상태
#### 행위
- `static register(MemberRegisterInfo, PasswordEncoder)`: 회원 등록
- `activate()`: 등록을 완료시킨다
#### 규칙
- 회원 생성후 상태는 등록 대기
- 등록 대기 상태에서만 등록 완료가 될 수 있다
```

주목할 점은 **메서드 시그니처를 실제 코드와 거의 동일하게 문서에 적는다**는 것이다
(`static register(MemberRegisterInfo, PasswordEncoder)`). 실제 `Member.java`를 확인하면
시그니처가 문서와 정확히 일치한다 — 이 문서는 사후 설명이 아니라 **코드 작성 전 설계도이자
계약서**로 쓰인 것으로 보인다. `_Aggregate Root_`, `_Entity_`, `_Value Object (record)_`,
`_Enum_`, `_Domain Service_`, `_Exception_` 같은 태그로 DDD 빌딩블록 종류를 항목마다 명시한다.

문서 하단에는 아직 상세화되지 않은 항목이 헤더만 비어있는 채로 남아있다(`### 강사`, `### 강의`,
`### 수업`... 내용 없음) — 완결된 문서가 아니라 계속 갱신 중인 리서치 문서라는 걸 스스로 드러낸다.

### 1-3. `도메인모델.drawio` — 관계/카디널리티 전용 다이어그램

draw.io(mxGraph XML) 원본 파일이 리포에 커밋되어 있다. 회원/강사/강의/수강/수업/섹션/진도 박스와
그 사이 연관관계에 카디널리티(`1`, `0..*`, `0..1`) 라벨이 붙는다. UML 클래스 다이어그램이
아니라 **개념 간 관계와 카디널리티만 표현하는 단순 박스-라인 다이어그램**이다(속성/메서드는 없음 —
그건 `도메인모델.md`가 텍스트로 맡는다). 즉 "다이어그램은 관계/카디널리티", "마크다운은
속성/행위/규칙"으로 **역할이 분담**되어 있다.

### 1-4. 코드와 문서의 연결 방식 — 하이퍼링크가 아니라 커밋 단위 동기화

코드 안에 문서를 가리키는 주석이나 `@see` 태그는 전혀 없다. 대신 커밋 히스토리를 보면 문서와
코드가 거의 항상 같은 커밋에서 함께 갱신된다.

```
5e32018 문서와 코드 다듬기
  domain/member/Member.java  |  9 +++--
  도메인모델.md               | 39 +++++++++++++++++-----
90890ed 회원 상세 정보 도메인 모델
  도메인모델.md               | 11 +++++++++++
c385a15 Member 도메인 로직 개발
  도메인모델.md               | 21 +++++++++++----------
```

패턴은 "먼저 `도메인모델.md`에 애그리게잇 설계(속성/행위/규칙)를 적고 → 다음 커밋에서 그 시그니처
그대로 코드를 구현"이다. 코드가 문서를 링크로 참조하는 게 아니라, **커밋 단위의 시간적 동기화**로
연결되어 있다.

### 1-5. `개발가이드.md` — 미니 ADR/아키텍처 원칙 문서

9줄짜리로 매우 짧지만 아키텍처 결정(헥사고날 아키텍처, 도메인 모델 패턴, 계층 흐름
`외부→어댑터→애플리케이션→도메인`, 패키지 구조 `application/required`/`application/provided`)을
담는다. 정식 ADR 포맷(Context/Decision/Consequence)은 아니고 결론만 적힌 "규약 노트"에 가깝다.

### Etude 적용 판단

- **그대로 적용 가능**: 용어사전의 "한국어-영어-설명" 3열 표 형식은 단순하고 즉시 적용 가능하다.
  `도메인모델.md`의 "속성/행위/규칙 + 빌딩블록 태그" 템플릿은 Etude의 `docs/glossary/`나
  `docs/specs/`에 애그리게잇 단위로 도입할 가치가 있다 — 특히 "메서드 시그니처를 문서에 먼저
  적고 코드로 옮기는" 워크플로우는 CLAUDE.md가 이미 명시한 "명세 선행(Spec-First)" 원칙과
  정확히 같은 방향이라 자연스럽게 맞물린다.
- **다르게 적용할 부분**: `.drawio`는 XML 바이너리에 가까워 diff 리뷰가 어렵다. Etude가 Git 기반
  협업/리뷰를 중시한다면 Mermaid(마크다운에 내장, diff로 변경 추적 가능)로 대체하는 편이 낫다.
  또한 코드-문서 간 명시적 링크가 없다는 점은 splearn의 약점으로 보인다 — Etude에서는 엔티티
  파일 상단에 관련 문서 경로를 한 줄 주석으로 남기는 정도로 보완할 만하다.
- **과할 수 있는 부분**: splearn은 단일 애그리게잇(`Member`)만 완성된 학습용 프로젝트라 문서
  부담이 크지 않다. Etude는 Phase 12까지 진행되어 도메인이 여러 개(`auth`, `user`, `quest`)이므로,
  모든 애그리게잇에 이 정도 상세 템플릿을 처음부터 유지하려 하면 비용이 커진다 — 핵심
  애그리게잇(예: `QuestSet`/`Quest`/`QuestSetAccess`) 먼저 적용하고 넓혀가는 게 현실적이다.

## 2. 프로젝트 구조 — 레이어 우선 + 헥사고날, ArchUnit으로 강제

패키지는 **레이어 우선**(`domain` / `application` / `adapter`) 구조이고, 그 안에서 `member`처럼
도메인별 하위 패키지로 나뉜다. 헥사고날 아키텍처를 명시적으로 채택했고 `application` 레이어는
`required`(아웃바운드 포트, 예: `MemberRepository`, `EmailSender`)와 `provided`(인바운드 포트,
예: `MemberRegister`, `MemberFinder`)로 분리된다.

흥미로운 점은 `HexagonalArchitectureTest.java`, `ArchUnitLearningTest.java`로 계층 의존 규칙을
**코드로 강제**한다는 것이다 — `개발가이드.md`에 적힌 원칙("도메인은 인프라를 모른다" 등)이 실제로
깨지지 않는지 테스트가 자동 검증한다.

**Etude 적용**: Etude도 CLAUDE.md에 "레이어는 자신의 역할만 안다"는 동일한 원칙이 이미 있다.
지금은 사람이 리뷰로 지키고 있는데, 프로젝트가 커지면 ArchUnit 같은 도구로 "도메인이 인프라 패키지를
import하면 빌드 실패" 같은 규칙을 테스트로 자동화하는 걸 고려할 만하다 — 지금 당장은 도메인
개수가 적어 급하지 않다.

## 3. 도메인 모델링 — 문서와 코드의 1:1 일치 확인

`Member` 애그리게잇 루트가 `MemberDetail`(1:1 엔티티, 프로필/자기소개/타임스탬프)을 캡슐화하고,
`Email`은 `domain.shared` 패키지의 값 객체(record)로 애그리게잇 경계를 넘어 공유된다. 상태 전이는
`MemberStatus` enum(`PENDING → ACTIVE → DEACTIVATED`)과 `Assert.state()` 가드로 표현되며,
실제 `Member.java` 구현이 `도메인모델.md`의 서술과 정확히 일치한다(`static
register(MemberRegisterInfo, PasswordEncoder)` 등). `PasswordEncoder`는 도메인 서비스
인터페이스로 도메인 레이어에 선언되고 `adapter/security`에서 구현되어, 도메인이 인프라에
의존하지 않는 전형적 포트 패턴을 보여준다.

**Etude 적용**: Etude의 `PasswordEncoder`(도메인 인터페이스)/`BCryptPasswordEncoderAdapter`
구조가 이미 정확히 같은 패턴이다 — 새로 배울 것은 적다. `MemberStatus` 같은 상태 enum +
`Assert.state()` 가드 방식은 Etude의 `UserRole`, `QuestSet.isPublic` 캡슐화와 방향이 같다.

## 4. 테스트 전략 (간단히)

`MemberFixture.java`로 테스트 객체 생성을 표준화하는 건 다른 두 프로젝트와 동일한 패턴이다(Etude의
`TestUsers`와 같은 방향). 새로운 점은 `ArchUnitLearningTest.java`/`HexagonalArchitectureTest.java`
처럼 **아키텍처 규칙 자체를 테스트로 강제**하는 것 — 문서(`개발가이드.md`)에 적힌 계층 규칙이
실제로 깨지지 않도록 자동 검증한다.

## 종합 판단: 지금 Etude에 적용할 만한 것

1. **`docs/glossary/`에 용어사전 표를 만든다** — splearn의 "한국어 | 영어 | 설명" 3열 형식을
   그대로 가져온다. 비용이 거의 없고, Etude가 이미 한국어 도메인 용어(퀘스트, 퀘스트셋, 접근
   권한 등)와 영어 코드명을 오가고 있어 바로 유용하다.
2. **핵심 애그리게잇에 "속성/행위/규칙" 구조화 문서를 시범 도입** — `QuestSet`/`Quest`/
   `QuestSetAccess`부터 시작해서, 새 Step을 시작하기 전에 이 형식으로 먼저 설계를 적어두면
   CLAUDE.md의 "명세 선행" 원칙과 자연스럽게 맞물린다. 모든 도메인에 한꺼번에 적용하지 말고
   다음 Step(Step 4 이후)부터 새로 쓰는 문서에 시범 적용.
3. **도메인 모델 관계도는 `.drawio`가 아니라 Mermaid로** — Git diff로 변경을 추적할 수 있게.
   `docs/glossary/`나 `docs/specs/`에 `mermaid` 코드 블록으로 애그리게잇 관계(카디널리티 포함)를
   그린다.
4. (더 나중, 도메인이 늘어났을 때) **ArchUnit으로 레이어 의존 규칙을 테스트로 강제** — 지금은
   도메인 개수가 적어 사람 리뷰로 충분하다.

우선순위는 1 → 2 → 3 순으로, 전부 "지금 하는 작업에 자연스럽게 끼워 넣을 수 있는" 낮은 비용의
개선이다. 4번은 프로젝트 규모가 커진 뒤에 재검토.
