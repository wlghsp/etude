### 테스트가 느렸던 원인 — PID 1과 SIGTERM

통합 테스트가 케이스당 정확히 10.3초씩 걸렸다. 원인은 정리 단계의 `docker stop`이었다.
컨테이너의 메인 프로세스(PID 1)가 `sleep 300`이면 SIGTERM을 무시해서 10초 뒤 SIGKILL까지
기다린다. `sh -c "trap 'exit 0' TERM; sleep 300 & wait"`로 바꾸면 0.14초로 줄었다.

- 전체 테스트: 1분 10초 → 약 39초. `DockerContainerRuntimeTest` 32초 → 2.3초.
- `exec sleep 300`은 `trap`을 써도 다시 10초로 돌아간다(`exec`가 핸들러를 없앰). 실측으로 확인.
- 문서로 남김: `docs/glossary/container_pid1_signals.md`.
- **실제 사용자 세션(`/bin/bash`, tty)도 `docker stop`에 10.2초가 걸린다**는 것을 실측으로 확인했다.
  지금은 사용자 응답 경로 밖이라 드러나지 않지만, graceful shutdown(Step 9)에서 컨테이너를
  순서대로 정리할 때 체감될 수 있다. Step 9 설계 시 다시 판단한다.

### 겪은 문제

- **`/grade`가 500, `container is not running` (409)**: 테스트의 `beforeTest`에서 `createContainer`만
  하고 `startContainer`를 빠뜨렸다. 만들기만 한 컨테이너에는 `exec`를 걸 수 없다.
- **"채점 명령이 실패하면" 케이스가 `passed: true`**: 시드 명령이 `["true"]`로 오타. `execAndCheck`
  구현은 정상이었다.
- **`QuestServiceTest`의 `verify(exactly = 0)`가 앞 케이스의 호출까지 셈**: mock이 스펙 최상단에서 한 번만
  만들어져 모든 케이스가 공유한다. `beforeTest { clearMocks(containerRuntime) }`로 해결.
  기존 테스트의 `verify(exactly = 0/1)`가 우연히 통과했을 가능성이 있다.
- **MariaDB 컨테이너 시작 실패(IDE 실행)**: 터미널의 `./gradlew`에서는 정상이었다. 이 머신은 Docker
  컨텍스트가 colima이고 `/var/run/docker.sock`이 없어서, IDE/Testcontainers가 소켓을 못 찾았을 가능성이 높다.
  (원인 확정은 못 함 — IDE에서 `DOCKER_HOST`를 지정하면 해결될 것으로 추정)
- **Gradle `configureEach ... cannot be executed in the current context`**: 재현 안 됨. Gradle 9.5.1과
  Kotlin 플러그인 2.0.20의 버전 간격이 의심되나 미확인. 반복되면 플러그인 버전 업그레이드를 따로 검토한다.

### 로컬 개발 환경 스크립트

`scripts/dev-up.sh`(DB + k3d, `--no-k8s`로 k3d 생략), `scripts/dev-down.sh`와
`docs/ops/guide_local_dev_env.md`를 만들었다. DB는 기존 `backend/docker-compose.yml`을 재사용한다.

- DB 준비 확인은 소켓이 아니라 TCP(`127.0.0.1`)로 한다. 첫 기동 때 MariaDB는 초기화 SQL을 돌리는 동안
  네트워크를 끈 임시 서버로 떠 있어서, 소켓 ping은 초기화가 끝나기 전에 성공해 버린다.
- **k8s 샌드박스를 로컬에서 쓰려면 `KUBECONFIG_PATH=$HOME/.kube/config-etude`가 필요하다.** 기본값
  `~/.kube/config`의 서버 주소는 `127.0.0.1:6443`이라 컨테이너 안에서는 클러스터에 닿지 않는다.
- 기존 `etude-db`의 볼륨에 예전 Node 스키마가 남아 있으면 `ddl-auto: validate`가 기동을 거부할 수 있다.
  (실제로 `dev-up.sh`는 아직 실행해 보지 않았다 — 문법 검사와 옵션 처리만 확인)
