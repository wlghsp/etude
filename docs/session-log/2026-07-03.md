### 퀘스트 현황 파악 + k8s 격리 방식 정리

팀원 계정을 열기 전에 현재 퀘스트 세트 현황(14개 세트, 132문항)과, 그중 "독립된 k8s 클러스터"(vcluster, `k8s-isolated`)를 쓰는 퀘스트가 무엇인지 확인.

- 결론: 현재 k8s 카테고리 4개 세트(6, 12, 13, 14번)는 전부 `sandbox_type='k8s'`(namespace 격리)이고, `k8s-isolated`를 쓰는 실제 세트는 DB에 하나도 없음(Phase 10 배관만 준비됨, 콘텐츠 없음)
- "기존 4개도 vcluster로 전환할까" 논의 → namespace 격리로 충분한 범위(pod/deployment/service/configmap 수준)라 전환 불필요, 대신 새 콘텐츠(RBAC/CRD/클러스터 운영, KLID CMP)만 `k8s-isolated`로 추가하는 방향으로 결정

### k8s namespace 고아 정리 논의 → Phase 6b 결정

**문제 제기**: 사용자가 "namespace도 vcluster처럼 잔여물이 남을 가능성이 높지 않냐"고 지적 — 실제로 `terminal.ts`의 `handleK8sTerminal()`이 `socket.on('close', ...)`에서만 namespace를 지우는데, 서버 비정상 종료(`kill -9`, 크래시) 시엔 이 경로가 안 탄다는 걸 코드로 확인. Docker 컨테이너(`cleanupOrphanContainers`)와 vcluster(`cleanupOrphanVclusters`)에는 이미 있는 고아 정리 안전망이 k8s namespace에는 없었음.

**Phase 6b 명세/가이드 작성**: `spec_phase6b_ns_cleanup.md`, `guide_phase6b_ns_cleanup.md` 신규.

**AI 역할 재확인**: "가이드를 준 뒤 사용자가 직접 구현"하는 방식으로 진행. 처음엔 정리 함수를 `terminal.ts`에 넣는 걸로 가이드를 썼으나, 사용자가 "docker.ts처럼 개별 파일이어야 하지 않냐"고 지적 — `terminal.ts`는 WebSocket 연결 처리가 본연의 역할이라 서버 기동 시 1회 실행되는 정리 로직을 얹으면 역할이 섞인다는 점에 동의, `plugins/k8s-namespace.ts` 신규 파일로 가이드 수정.

**사용자가 직접 구현**: `backend/src/plugins/k8s-namespace.ts` 작성, `index.ts`에 배선.

### vcluster pool 재사용 아이디어 논의 → 보류 결정

사용자가 "vcluster 2개 생성이 쉽지 않은데, 서버 재시작 시 기존 vcluster를 지우지 말고 재사용하면 기동 속도를 높일 수 있지 않냐"고 제안. 실제로 지금 `initPool()`은 재시작마다 기존 vcluster를 전부 지우고 새로 만드는 낭비가 있다는 점에 동의.

다만 논의 중 사용자가 스스로 반박 — "재사용했는데 기존에 사용했던 클러스터라 깔끔하지 않다면 실습자에게 제대로 된 환경을 제공 못하게 되는데?" 실제로 서버 재시작 시점에는 "pool에서 대기만 하다 죽은 vcluster"와 "실습 중이었는데 서버가 죽어서 releaseVcluster()를 못 받은 vcluster"를 구분할 방법이 없다는 게 핵심 문제 — `releaseVcluster()`가 원래 "재사용하지 않음, 항상 삭제" 정책이었던 이유와 정확히 충돌. **결론: 재사용 최적화는 보류, 기존 방식(무조건 삭제 후 재생성) 유지.**

### Phase 6b 검증 중 혼선 — 정상 종료 vs 비정상 종료 경로 구분

사용자가 "서버 종료만 해도 quest-namespace가 정리된다"고 보고 → `kill -9` 직후 확인한 것으로 재확인. `index.ts`의 `onClose` 훅에는 `cleanupOrphanVclusters()`만 있고 `cleanupOrphanQuestNamespaces()`는 없다는 걸 코드로 재확인 — 즉 그 정리는 Phase 6b(기동 시 정리)가 아니라 `terminal.ts`에 원래 있던 정상 종료 경로(`socket.on('close', ...)`)가 작동한 것으로 결론. 두 로직(정상 종료 시 즉시 정리 vs 비정상 종료 후 다음 기동 시 정리)은 서로 다른 경로를 커버하는 상호 보완 관계이므로 Phase 6b를 지울 이유 없음 — 그대로 유지 결정. 검증 재현 순서(kill -9 → 서버 꺼진 채로 확인 → 재기동 → 재확인)를 다시 안내.

### Phase 7i 구현 — 사용자가 대부분 직접 진행 + 마무리는 AI가 지원

사용자가 가이드를 보고 백엔드(`services/user.ts`에 `changeOwnPassword` 추가 — 가이드는 `services/auth.ts`를 제안했으나 `resetPassword`와 같은 파일에 두는 게 낫다고 판단해 다르게 배치, 합리적 선택으로 그대로 인정)와 프론트 대부분을 직접 구현.

마지막에 `<ChangePasswordModal>`을 `App.tsx`의 어디에 넣어야 할지 몰라 AI에게 요청 — `SideNav`가 쓰이는 4개 페이지 분기(`progress`/`leaderboard`/`admin`/`home`) 각각에 기존 `<FeedbackButton>`과 같은 패턴으로 추가. `tsc --noEmit` 통과 확인 후 사용자가 브라우저에서 직접 테스트 완료.
