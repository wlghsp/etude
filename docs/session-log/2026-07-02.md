### Phase 8 — OCI 서버 실제 프로비저닝 완료 (ARM Always Free 용량 확보)

전날 밤부터 `retry_apply.sh`로 재시도하던 ARM Always Free 용량 부족이 계속 이어짐.

- 사용자가 OCI 계정을 Pay As You Go(유료 티어)로 업그레이드 — Always Free 리소스 자체는 계속 무료(과금 없음)이고, Free Tier 계정보다 유료 계정이 ARM 용량 배정 우선순위가 높다는 점을 근거로 추천, 사용자가 진행
- 오사카 리전은 가용성 도메인(AD)이 1개뿐이라 "다른 AD로 재시도"가 애초에 불가능하다는 점 확인 (`terraform console`로 조회)
- 홈 리전(오사카)은 계정 생성 후 변경 불가라는 점 재확인 — 다른 리전은 추가 구독만 가능하고 Always Free 할당은 계정당 한 리전에만 적용되는 것으로 판단
- 업그레이드 후 재시도 끝에 VM 생성 성공

**공인 IP 충돌 발견 + 해결**

- VM 생성 시 `assign_public_ip = true`로 임시(ephemeral) 공인 IP가 자동 할당되는데, `main.tf`가 별도로 Reserved Public IP를 만들려다 `already has a public IP` 충돌 발생
- `assign_public_ip = false`로 변경해 임시 IP를 아예 안 받고 Reserved IP만 쓰도록 정리 — Always Free 한도(IPv4 1개) 안이라 과금 없음을 확인 후 진행
- 최종 공인 IP `161.33.45.200` 확보

### Phase 8 — docker compose 실행 중 연쇄적으로 발견한 문제 4건 (전부 실제 배포로 재현 후 수정)

**1. `--project-directory` 누락으로 `.env.prod` 못 찾음**

`deploy/` 안의 compose 파일을 `-f deploy/docker-compose.prod.yml`로 실행하면, 파일 내부 상대경로(`./backend/.env.prod` 등)가 **compose 파일 위치(`deploy/`) 기준**으로 해석되어 실제로는 존재하지 않는 `deploy/backend/.env.prod`를 찾음. `--project-directory .`를 추가해 프로젝트 루트 기준으로 해석되도록 수정. 가이드의 모든 `docker compose -f deploy/...` 명령(6곳)에 일괄 반영.

**2. `${DB_USER}`/`${DB_PASSWORD}` 변수 치환이 `env_file`로는 안 됨**

`env_file`은 컨테이너 안에 환경변수를 주입하는 설정이고, compose 파일 자체의 `${VAR}` 치환은 `--project-directory` 위치의 `.env` 파일(정확히 이 이름)이나 셸 환경변수만 본다는 걸 확인 — 두 메커니즘이 별개라는 걸 놓쳐서 "not set" 경고 발생. 프로젝트 루트에 별도 `.env` 파일을 추가하는 Step 6-4를 가이드에 신설.

**3. `vcluster: not found` — backend 컨테이너에 CLI 바이너리 없음**

DB_USER/PASSWORD 문제 해결 후 backend가 계속 재시작을 반복 — 로그 확인 결과 `vcluster-pool.ts`가 backend 프로세스 자신이 직접 `vcluster`/`kubectl` 명령을 실행하는 구조인데, `backend/Dockerfile`에 두 바이너리가 설치되어 있지 않았음. (`k8s` 네임스페이스 격리 타입은 `etude-k8s` 컨테이너 안에서 `docker.exec()`로 실행되어 이 문제가 없었지만, vcluster pool은 backend 자체에서 실행되는 구조적 차이가 원인.) Dockerfile에 `kubectl`/`vcluster` 설치 단계 추가.

**4. `KUBECONFIG` 환경변수 없어 vcluster CLI가 설정을 못 찾음**

바이너리 설치 후에도 `no configuration has been provided` 에러로 재시작 반복. vcluster CLI는 표준 `KUBECONFIG` 환경변수(또는 `~/.kube/config` 기본 경로)를 보는데, 마운트된 kubeconfig 경로가 비표준(`/root/.kube/config-etude`)이라 인식 못 함. `docker-compose.prod.yml`의 backend 서비스에 `KUBECONFIG: /root/.kube/config-etude` 환경변수 추가로 해결.

### Phase 8 — 로그인 405 에러 → nginx 라우팅 설계 자체가 잘못됨을 발견

브라우저에서 로그인 시도 시 `405 Not Allowed`. 원인 조사 결과, `nginx.conf`가 `/api/`로 시작하는 요청만 backend로 프록시하도록 되어 있었는데, 실제 백엔드 라우트(`auth.routes.ts` 등)는 `/api` 접두사 없이 `/auth/login`, `/quest-sets`처럼 등록되어 있어 애초에 안 맞는 설계였음 — Step 7-2 가이드 자체가 처음부터 이 불일치를 안고 있었음.

**해결**: 프론트가 SPA 라우터 없이 `App.tsx` state로만 화면을 전환해 실제 경로가 `/` 하나뿐이라는 특성을 이용 — 정적 파일이 존재하면 서빙하고, 없으면 전부 backend로 넘기는 방식(`try_files ... @backend`)으로 재설계. `location = /`(정확히 루트)와 `location /`(나머지)를 분리해 `index.html` 우선 서빙도 유지.

`--force-recreate` 없이는 nginx가 마운트된 설정 파일 변경을 감지 못하고 기존 컨테이너를 그대로 유지한다는 점도 확인 (compose가 YAML 자체 변경 여부만 보고 볼륨 내용 변경은 추적하지 않음).

**최종 검증**: 브라우저에서 로그인 성공 확인 — Phase 8 배포 완료.
