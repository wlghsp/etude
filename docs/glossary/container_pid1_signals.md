# 컨테이너 PID 1과 종료 신호 (SIGTERM)

## 한 줄 요약

컨테이너의 첫 프로세스(PID 1)는 **종료 신호(SIGTERM)를 기본으로 무시한다.**
그래서 `sleep 300`으로 띄운 컨테이너는 `docker stop` 때 10초를 꽉 채워 기다리고,
`trap`으로 신호를 받게 만든 셸은 즉시 끝난다.

```kotlin
// 느림 — docker stop에 10초
command = listOf("sleep", "300")

// 빠름 — docker stop에 0.14초
command = listOf("sh", "-c", "trap 'exit 0' TERM; sleep 300 & wait")
```

이 문서는 "왜 이 한 줄이 10초를 없애는가"를 풀어 쓴다.

---

## 1. 배경: 이 문제를 어디서 만났나

Phase 12 Step 7의 통합 테스트(`QuestGradeControllerTest`, `DockerContainerRuntimeTest`)는
테스트마다 컨테이너를 하나 띄우고, 끝나면 `stopAndRemove`로 지운다.
컨테이너 안에서 채점 명령을 `exec`로 실행해야 하니 컨테이너가 **살아 있어야** 해서,
`sleep 300`을 메인 프로세스로 줬다.

그런데 테스트 케이스마다 정확히 10.3초씩 걸렸다. 테스트 로직은 몇 밀리초면 끝나는데도.

| 상태 | 케이스당 시간 | 6개 합계 |
|------|--------------|---------|
| `command = ["sleep", "300"]` | 약 10.3초 | 약 62초 |
| `command = ["sh", "-c", "trap ... wait"]` | 약 0.5초 | 약 3초 |

원인은 테스트가 아니라 **정리 단계(`afterTest`의 `docker stop`)** 에 있었다.

---

## 2. `docker stop`은 어떻게 동작하나

```
docker stop <컨테이너>
   │
   ├─ 1) PID 1에게 SIGTERM 전송   ("정리하고 종료해 주세요")
   │
   ├─ 2) 최대 10초 대기 (기본값)
   │       └─ 그 안에 종료하면 → 끝
   │
   └─ 3) 안 끝나면 SIGKILL 전송   ("강제 종료")  ← 커널이 즉시 죽임
```

**SIGTERM** 은 "정중한 종료 요청"이다. 받은 프로세스가 스스로 정리하고 끝낼 수 있다.
**SIGKILL** 은 프로세스가 거부할 수 없는 강제 종료다.

핵심은 1단계에서 PID 1이 SIGTERM을 받고도 가만히 있으면, 2단계의 10초가 그대로 낭비된다는 점이다.

---

## 3. 왜 PID 1은 SIGTERM을 무시하나

리눅스 커널은 PID 1에게만 특별한 규칙을 적용한다.

> PID 1은 **직접 시그널 핸들러를 등록하지 않은** 시그널은 무시한다.
> (일반 프로세스는 핸들러가 없으면 SIGTERM에 의해 기본 동작으로 종료된다.)

이유는 PID 1이 시스템의 최상위(init) 프로세스이기 때문이다. 실수로 죽으면 시스템 전체가
무너지므로 커널이 "명시적으로 처리하겠다고 밝힌 신호만 받는다"는 보호 장치를 둔 것이다.

컨테이너는 자기만의 PID 네임스페이스를 가지므로 **컨테이너 안의 첫 프로세스가 곧 PID 1** 이 된다.

| 컨테이너 command | PID 1 | 이 프로세스의 SIGTERM 핸들러 | 결과 |
|------------------|-------|----------------------------|------|
| `sleep 300` | `sleep` | 없음 (`sleep`은 신호를 직접 처리하지 않음) | 무시 → 10초 대기 후 SIGKILL |
| `sh -c "trap 'exit 0' TERM; ..."` | `sh` | **있음** (`trap`이 등록) | 즉시 종료 |

즉 `sleep`이 특별히 나쁜 게 아니라, **"PID 1 자리에 있으면서 SIGTERM 핸들러가 없는 프로세스"** 가
문제다. `sleep`은 일반 프로세스로 돌 때는 SIGTERM에 잘 죽는다.

---

## 4. 바꾼 명령을 한 조각씩

```
sh -c "trap 'exit 0' TERM; sleep 300 & wait"
```

| 조각 | 의미 | 없으면? |
|------|------|--------|
| `sh -c "..."` | 셸이 문자열을 명령으로 실행. 셸이 PID 1이 된다 | — |
| `trap 'exit 0' TERM` | **SIGTERM이 오면 `exit 0`을 실행**하라고 핸들러 등록 | PID 1이 SIGTERM을 무시 → 10초 |
| `sleep 300 &` | `sleep`을 **백그라운드**로 실행 (`&`) | 아래 `wait`가 기다릴 대상이 없음 |
| `wait` | 백그라운드 작업이 끝날 때까지 셸이 대기 | 셸이 바로 끝나서 컨테이너가 즉시 종료됨 |

`;` 는 명령 구분자이므로 전체는 **"핸들러 등록 → sleep을 뒤에서 돌리고 → 셸은 기다린다"** 순서다.

### 왜 `sleep 300`을 그냥 실행하지 않고 `& wait`로 돌리나

`sleep 300`을 포그라운드로 실행하면 셸이 `sleep`이 끝날 때까지 블록된다.
bash는 포그라운드 명령이 끝나기 전까지 `trap` 핸들러 실행을 미루기 때문에,
SIGTERM이 와도 `sleep 300`이 끝나는 300초 뒤에야 핸들러가 돈다.

반면 `wait` 는 시그널이 오면 **즉시 중단되고 핸들러가 바로 실행**된다. 그래서
`sleep &` + `wait` 조합을 쓴다.

종료 후 남는 백그라운드 `sleep` 프로세스는 컨테이너가 사라지면서 함께 없어진다.

## 5. 직접 확인한 결과 (실측)

`etude-linux` 이미지에서 컨테이너를 띄우고 `docker stop` 시간을 쟀다.

| command | 시간 | 해설 |
|---------|------|------|
| `sleep 300` | **10.17초** | PID 1 = sleep, 핸들러 없음 |
| `sh -c "sleep 300"` | **10.24초** | PID 1은 `dash`(셸)지만 SIGTERM 핸들러(`trap`)가 없어서 똑같이 무시한다. 셸이라고 자동으로 신호에 반응하는 게 아니다 |
| `sh -c "trap 'exit 0' TERM; exec sleep 300"` | **10.20초** | `exec`가 셸을 `sleep`으로 갈아치움 → `trap`도 함께 사라짐 |
| `sh -c "trap 'exit 0' TERM; sleep 300 & wait"` | **0.14초** | PID 1 = sh, 핸들러 유지 |
| `/bin/bash` (대화형, tty) | **10.23초** | 실제 사용자 세션과 같은 구성. 7번 참고 |
| `--init` 옵션 + `sleep 300` | **0.16초** | 아래 6번 참고 |

세 번째 행이 중요하다. `trap`을 써도 `exec`를 붙이면 **프로세스가 교체되며 핸들러가 사라진다.**
"trap이 있으니 괜찮겠지" 하고 `exec sleep 300`으로 쓰면 다시 10초로 돌아간다.

## 6. 다른 해결 방법

| 방법 | 설명 | 이 프로젝트에서 |
|------|------|----------------|
| **`trap` + `wait`** (현재 선택) | 명령 한 줄만 바꾼다. 컨테이너 생성 옵션 변경이 없다 | 테스트 코드만 수정하면 되어 가장 작은 변경 |
| **`docker run --init`** | Docker가 가벼운 init(tini)을 PID 1로 넣고, 그 아래에서 `sleep`을 실행. 신호를 자식에게 전달해 준다 | `ContainerSpec`/`createContainer`에 옵션 추가 필요 — 프로덕션 코드 변경 |
| **`stop` 타임아웃 단축** | `stopContainerCmd(...).withTimeout(1)`로 SIGKILL까지 대기를 1초로 | 실제 사용자 컨테이너의 정리 동작이 바뀜 |
| **`kill` 후 remove** | `stop` 없이 강제 삭제 | 정상 종료 기회를 안 줌 |

테스트 때문에 프로덕션 정리 동작을 건드리고 싶지 않아서, **테스트가 띄우는 컨테이너의
command만 바꾸는** 첫 번째 방법을 골랐다.

---

## 7. 이 프로젝트의 실제 사용자 컨테이너는?

실제 사용자 세션의 컨테이너는 `command = ["/bin/bash"]`, `tty = true`, `openStdin = true`로 뜬다
(`TerminalSessionService.openDefault`). 같은 구성으로 재 봤더니 **이것도 `docker stop`에 10.23초**가
걸렸다. 대화형 bash가 PID 1이어도 SIGTERM을 기본으로 무시하기 때문이다.

즉 이 현상은 테스트용 컨테이너만의 문제가 아니라 **지금 운영 코드의 `stopAndRemove`도 컨테이너를
지울 때마다 최대 10초씩 걸린다**는 뜻이다. 사용자 응답 경로를 막지 않는 곳(세션 종료 후 정리)이라
드러나지 않았을 뿐이다. 다만 아래 경우에는 체감될 수 있다.

- 서버 종료(graceful shutdown) 시 남은 컨테이너를 순서대로 정리할 때 (Step 9)
- 고아 컨테이너 일괄 정리(`ContainerCleanupService`)에서 컨테이너가 많을 때

이 부분을 줄일지(예: `stop` 타임아웃 단축, 생성 시 `--init`)는 운영 코드 변경이라 이번 Step 7
범위에서는 건드리지 않고, **Step 9(세션 종료/graceful shutdown)를 설계할 때 다시 판단한다.**

## 8. 한 줄 정리

> 컨테이너의 PID 1은 SIGTERM 핸들러를 직접 등록하지 않으면 SIGTERM을 무시한다.
> `trap`으로 핸들러를 등록하고, `wait`로 기다리게 만들면 `docker stop`이 즉시 끝난다.
> `exec`를 붙이면 핸들러가 사라지니 주의.
